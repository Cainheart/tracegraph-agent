## 0. 本文使用说明（给执行者）

### 0.1 这份文档要解决什么

TraceGraph Agent（`tracegraph-agent/`）当前是 P0 `v0.1-alpha`：它证明了「可检查的 Agent Harness 纵向链」——契约层 → Runtime → 工具、权限与审批 → 事件账本 → 投影 → Host/SDK → Web 工作台。G-19 凭据安全、G-01 会话持久化/恢复、G-03 token 计量/usage 回填、G-04 Action WAL、G-02 Context 策略链/模型摘要/原文外置、G-05 工具输出契约/批调度、G-13 `run_test` 子进程沙箱、G-06 权限预设/策略引擎/一次性审批 token、G-09 Plan/Todo、G-10 Skill、G-11 MCP stdio/native bridge、G-12 LSP stdio/native client、G-14 运行中 steering、G-15 vendor-neutral Telemetry/OTLP-HTTP 旁路、G-16 离线行为/质量/性能/文档评测、G-17 受信扩展生命周期、G-18 附件与多模态、G-08 root-Ledger Agent Team、G-20 有界静态 CodeIntel/Git 审批漂移防护，以及 G-22 CI/覆盖率/供应链/私有构建发布纪律已经落地；它**仍不具备**MCP 的 PTC/HTTP/SSE/resources/instructions、完整动态调用/DI/路由/跨语言代码语义、跨 Host Team consensus/worker 自动恢复、任意第三方插件加载/隔离/分发、跨平台完整沙箱、完整 OTel SDK/平台集成、真实 provider/浏览器评测与已取得 URL 的 GitHub-hosted CI 运行证明等成熟 harness 外围能力。

本文把缺口逐条列出来，并为每条给出：**现状证据 → 参考实现（具体到文件） → 仿照方案（具体到契约与文件） → 验收标准 → 工作量**。

### 0.2 执行者必须遵守的既有约束（不可破坏）

1. **事件账本是唯一事实来源**：任何新能力产生的持久事实必须落成 `SessionEvent`（`packages/contracts/src/event.ts`），不得另建并行日志格式。
2. **契约先于实现**：新增能力先在 `packages/contracts` 定义 Zod schema，再在 `packages/core` 实现；跨进程边界（SDK/Host/Web）只能传契约类型。
3. **fail-closed**：审批、策略、沙箱、凭证一律"不确定即拒绝"。
4. **append-only + 可重放**：投影必须能由账本重放得到；不得让内存态成为必要事实。
5. **不改既有事件语义**：新增事件类型只能**追加**到 `EventTypeSchema` 枚举，且 `SCHEMA_VERSION` 需按既有规则演进（见 `packages/contracts/src/common.ts`）。
6. **测试必须与实现同 PR**：本工程的惯例是"契约测试 + 集成测试"双层（`packages/contracts/src/contracts.test.ts`、`packages/core/src/runtime.ts` 对应的 `runtime.integration.test.ts`）。

1. 契约 `packages/contracts/src/session.ts`：

   export const SessionHeaderSchema = z.object({
     kind: z.literal("header"),
     session_version: z.literal(SESSION_FORMAT_VERSION),
     session_id: IdentifierSchema,
     project_id: IdentifierSchema,

   所有条目带 `entry_id` / `parent_entry_id`（对齐 pi 的树模型，为"从某条消息分叉重跑"预留）。
2. `packages/core/src/session-store.ts`：

3. 实际恢复编排位于 `packages/core/src/session-controller.ts`（没有另建 Host 私有恢复格式）：启动时扫描全部会话文件 → 逐行解析，尾部残行在 lease 内 **truncate** 并落 `session.tail_truncated`；对无终态的 Run 落 `run.interrupted`，投影状态为 `interrupted`；恢复报告进启动日志与 `/api/bootstrap.recovery`。
4. 追加事件类型：`session.opened`、`session.closed`、`session.title_changed`、`session.tail_truncated`、`run.interrupted`、`run.resumed`。
5. **明确边界**
- Session JSONL 只存 header 与 `event_ref`，canonical Event Ledger 仍是唯一事实来源；恢复上下文/待审批 Patch 不写进 Session 文件。
- `event_ref` 不含 ledger data-root locator；一个 Session root 必须与创建它的同一 `dataDir` 稳定配对，不能跨多个独立 Ledger 共用。配对错误在启动扫描时 fail-closed。
- Ledger 先提交、Session ref 后追加；两步之间崩溃会留下“Ledger 有事实、索引缺引用”的窗口。G-01 以 Ledger 为权威；G-04 会在恢复特定 Patch Action 时以稳定幂等提案补齐其 Event ref，但没有对所有历史事件做通用反向索引扫描。
- 待审批 Patch 可恢复到“再次等待用户审批”，旧 approval 无效；G-09 的待审批 Plan 可恢复原 `plan_event_id`/Todo revision，但仍需显式批准。缺失或篡改恢复 Artifact 时 fail-closed；其它非终态阶段的 resume 只追加只读恢复事实，仍保持 `interrupted`。
- 恢复 Artifact 不进入 Session JSONL 或公开 Wire；内部 8 MiB 不是任意大文件通道。Artifact root/文件以 `0700`/`0600` 收紧并拒绝 symlink root，但本地权限不等同于静态加密。
- 第二 writer 会被拒绝且文件保持完整；Host 以脱敏结构化字段记录 `session.operation_rejected`（code/status/method/route），不记录后端 lock path/PID/hostname。审计刻意落在 Host 边界，不能为了给冲突本身记账而绕过争议中的 Session lease。

**实现证据**

**参考实现**

| 仓库 | 文件 | 关键机制 |
| --- | --- | --- |
| dsh | `docs/subsystems/compaction.md` | 压缩是**可替换的 surface operation**：产物写成新的 surface node，不就地改历史；`packages/compaction/` 按策略拆包（基础压缩、`compaction-tool-result-pruner`、`compaction-image-offload`） |

**已落地的策略与时序**

1. 默认链严格按 `tool_output_pruner → spill → model_summary → tiered_checkpoint` 执行，每步可独立关闭。默认阈值/目标为 `3_000→1_500`、`12_000→preview 800`、`24_000→4_096`（15s）、`24_000→4_096`。

2. `commit_patch` 的成功路径固定为：before-image + `prepare` → 临时文件写入/fsync/rename/目录 fsync → 重新读取并核对 after hash → `applied` → `tool.completed` Receipt/Observation 与 `patch.applied` → `committed`（绑定 event/receipt id）→ `action.verified` → `verified`。任一步的注入崩溃均留下可判定的最近 phase。

**实际落地机制**

1. 三种内置预设是不可拆开的命名组合：`read-only = read-only sandbox + never`，`workspace-write = workspace-write sandbox + on-write`，`full-write = danger-full-access + never`；默认与默认 ceiling 均为 `workspace-write`。preset 还携带 Tool allowlist 与 workspace-relative path scope，浏览器不能分别提交 sandbox、approval policy、rules 或 path。
2. 每个 Tool action 先受不可委托的 Workspace capability、plan mode、preset allowlist、read-only write 与 path scope 约束；这些 hard constraint 命中后，任何 `allow` 规则都不能覆盖。Host 规则按 `priority` 降序，同优先级按 `deny > ask > allow`、再按 `rule_id` 稳定排序；`tool / side_effect / path_glob / max_diff_lines / session_tags` 是合取条件。项目规则只接受 `ask/deny`，作为独立层进一步收紧 Host 结果，不能增加 allow。
3. 配置优先级分成“上限”和“选择”两步：`--permission-preset` 高于 `TRACEGRAPH_PERMISSION_PRESET`；旧 `--sandbox-mode` / `TRACEGRAPH_SANDBOX_MODE` 只作兼容映射，若与新配置冲突则拒绝启动；都未设置时 ceiling 为 `workspace-write`。用户/Web 选择持久化到私有 `harness-config.json`，只能等于或低于 ceiling；项目 `policy.json` 最后叠加且只能收紧。设置变更只影响之后创建的 Run。
4. Runtime 为每个新 Run 解析一次 `EffectivePermissionPolicy`，稳定 digest 包含 preset 与分层的 Host/project rules；`permission.configured` 与每次 `policy.evaluated` 保存可解释的 source、rule id、priority、explanation 与 policy digest。effective policy 连同分层来源写入当前 v3 内部 recovery Artifact，恢复时沿用原 digest 与语义，而不是按当前设置重新求值。
5. Patch 的 `action_digest` 绑定 project/run/action/tool/workspace handle、policy digest、规范化参数/路径/target、base/patch hash 与 scope；执行绑定另保留 canonical target digest，并在 `patchMutation.prepare`、WAL 之前再次核对，防止批准后换到同内容 symlink 目标。执行 Tool 前 Runtime 还会用该 Run 冻结的 effective policy 做最终重评；若已收紧为 `deny`，则在 `tool.started`、WAL 和 mutation 前以 `capability_denied` 终止。只有最终决策为 `ask` 时，grant 才由 Host 签发短期、单次、进程内 token；消费同时校验 approval/project/run/action、action digest、policy digest、scope 与 expiry，任何失配都会先 burn 再拒绝，重复消费必拒绝。未被规则收紧的 `full-write` 是 `allow`：它不创建 `approval.requested` / `approval.granted`，也不签发或消费 token，但仍重算 canonical action digest 并进入同一 Workspace/hash/WAL 提交边界。非 Patch `ask` 走可信 Host `approvalAnswerer`；Patch `ask` 仍由 Web/SDK 手工 approve/reject。answerer 缺失、抛错、返回非法值或拒绝时均 fail-closed，不把“无法询问”解释成 allow。

**实际落地机制**
1. `submitUserInput()` 先在 canonical Ledger 落 `user.input_queued`；namespaced `command:${sha256(command_id)}:user.input_queued` 避免 hostile id 与 terminal/consumed/WAL key 碰撞。`command_id` 与 `input_id` 均按原始 payload digest 幂等，同 payload retry 返回 canonical duplicate，异 payload（包括脱敏后文本碰撞）fail-closed；换 command id 的同一输入会 durable 绑定 alias，重启后也不能改绑。普通 message/hint 只可占 99 个槽，最后一槽为紧急 cancel 保留，队列总上限 100。
2. **安全点消费**只发生在工具批次结束后、下一次 Context/model 请求前；每个 safe step 仅取普通输入 FIFO 队头一条，先落 `user.input_consumed{at_step}`，再作为 user history 进入下一次请求。Runtime 会先证明还有下一次 model turn，避免留下“已消费但没有下一请求”的假事实。如果输入在 model 返回 finish 期间到达，共享 control gate 让 durable queue 胜出，不会先写终态而丢消息。
3. `cancel` 一律先 durable 入队再 abort 当前 model；它是 control-lane 例外，可越过最多 99 条更早的普通输入，被越过者继续保持 pending。Tool 已运行时，Runtime 等待 batch/cancellation shield 到安全边界，再落 consumed 与唯一 `run.cancelled{reason:"user_cancel",last_sequence}`；batch start、审批、Plan/Todo mutation、preview 与新 Tool start 都在同一取消 authority gate 上线性化。已跨过 atomic rename/WAL 边界的 Patch 会完整收口，不会留半写，也不会自动回滚。
4. `projectRun()` 由 queued/consumed Event 重建 pending 和 last-consumed；重启保留未消费输入，并从 Ledger 补回“consumed Event 已落、进程内 history 未更新”崩溃窗口。Ledger commit 后 Session ref/响应丢失的 retry 会重放并补索引、重新武装 cancel/finalizer；cancel 已 consumed 但终态未落时补唯一 cancelled。普通 `interrupted` Run 仍保持 G-01 只读语义；若 prior running/indexing/待批 Run 已有 durable pending cancel，用户显式 resume 只运行最小 consume+cancel 收口，不重发旧 indexing/model/tool。

Host 从 route/current Projection 绑定 project/run/actor，SDK 对 request/result 双重校验。Web 在 running/indexing/待 Plan 或 Patch 审批时保留 `SteeringComposer`，显示 pending 与 `at_step`；readonly workspace 也可写 Run Ledger，但 interrupted/manual/terminal 不接受新 steering。Web 在未知响应重试时复用同一组 id，用 `last_sequence` 单调门与 Run generation/current-run guard 拒绝旧投影及跨 Run 晚响应；紧急 cancel 有独立 busy 通道。

## 6. 不建议照搬的部分（防止过度设计）

| 不要做 | 原因 |
| --- | --- |
| **通用依赖注入 / 插件内核（Cordis 那一层）** | dsh 的"一切皆插件"需要 60+ 包与巨大的间接层；TraceGraph 当前约 18.5k 行源码，照抄仍会显著破坏可读性。G-17 只做 6 个有界扩展点的**最小**版本 |
| **把 Python 侧当作第二实现（claw-code 的 PARITY 模式）** | 双实现只对"行为对等验证"这个特定目标有价值；本项目没有这个需求，代价是两倍维护量 |
| **自带 TUI** | pi/dsh 有 TUI 是因为它们定位终端工具；TraceGraph 是 Web 工作台 + CLI 装配器，TUI 是纯负债 |
| **自建权限系统之外的"全权限默认"** | pi 明确选择"默认全权限、安全交给容器"；TraceGraph 已有审批链，**放弃 fail-closed 去换便利是倒退** |
| **把有界 G-08 误写成分布式 Agent Team scheduler** | 已实现的是单 Host、root-Ledger 驱动的 roster/mailbox/task board 与显式 heartbeat/sweep；没有跨 Host consensus、后台 worker 自动恢复、任务自动重派或通用非阻塞父模型循环 |
| **远程/SSH/容器执行** | 与"本地可审计单人工作台"的定位冲突；G-13 当前仅覆盖本地 `run_test` child，仍不据此扩展远程/容器执行 |
| **向量库/嵌入模型的强绑定** | 参考 claw-code 的教训：RAG 服务应可替换后端（G-21 一期只用本地 BM25+JSONL） |
| **引入模型 SDK（openai/anthropic 官方包）** | 现状用纯 `fetch` 实现两条协议，这是本项目"零重依赖"的优点，别破坏 |
| **为了覆盖率而写测试** | dsh 的 100% per-file 覆盖是**结果**不是手段；本项目应先保证"每条新机制有 1 个失败注入测试" |
