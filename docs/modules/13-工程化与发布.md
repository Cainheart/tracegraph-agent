# 模块 13：工程化与发布

> 定位：G-22 的可执行质量门、供应链约束、私有 workspace 与本机安装包发布纪律。
> 入口：`.github/workflows/`、`vitest.coverage.config.ts`、`scripts/`  
> 最后核对：2026-10-03

## 1. 本地与 CI 命令

```bash
pnpm verify:lockfile
pnpm supply-chain:check
pnpm typecheck
pnpm test
pnpm test:e2e
pnpm coverage
pnpm evals
pnpm release:check
pnpm release:bundle
```

`pnpm build` 的第一步是 `pnpm clean:dist`。清理器只接受 `apps/*`、`packages/*` 下具有安全 `package.json` 的 manifest-owned `dist`，拒绝 symlink，并且不会清理任意匹配名称或仓库外目录。这样发布校验读取的是本次构建产物，而不是历史构建残留；`clean-dist.test.mjs` 用 rogue 目录和 symlink 反例锁定该边界。

工程 CI 的三个 job 相互独立；标签发布工作流另有安装包矩阵和 workspace 归档 job（见第 7 节）：

| Job | 必须成功的边界 |
|---|---|
| `typecheck` | frozen install、lockfile guard、先 clean build 再做全包/评测类型检查、release shape；不依赖旧 `dist/*.d.ts` |
| `test` | high/critical audit、unit/integration、CLI E2E、覆盖率门、coverage artifact |
| `evals` | 清空 provider/OTLP 凭据后运行 G-16 离线评测并上传 bounded report |

三个 job 的安装顺序固定为：`pnpm/setup install:false` → 直接执行 `node scripts/verify-lockfile.mjs --skip-frozen` → `pnpm install --frozen-lockfile` → 完整 lockfile/测试门。预安装阶段刻意不经 `pnpm <script>` 分派，避免任何宿主脚本包装器先做隐式安装；manifest/config 级的 direct source、range、override 与 pnpm pin 问题会在依赖 lifecycle script 有机会运行前失败。安装后的 `verify:lockfile` 再做 frozen drift 核验。

工作流仅授予 `contents: read`，checkout 不持久化凭据；第三方 Actions 使用完整 commit SHA，pnpm 与 Node 使用精确版本。PR 不能通过修改浮动 tag 在下一次运行时悄悄更换 Action 实现。仓库内可验证工作流结构及同构本地命令，但当前没有可引用的 GitHub-hosted run URL，因此不能把“workflow 已定义/本地已通过”写成“远端 CI 已成功运行”。

## 2. 覆盖率门

`pnpm coverage` 先产生 V8 JSON summary，再由仓库脚本独立核对：

- 全局 line coverage 不低于 70%；
- `packages/contracts/src/**` 聚合 line coverage 不低于 90%；
- `packages/context/src/context.ts` 与 `packages/tool/src/policy-engine.ts` line coverage 不低于 90%。

校验器拒绝缺失、空、越界、非有限或路径逃逸的 coverage 输入。专用失败注入测试会人为降低命中数，证明阈值并非只写在配置中而没有执行。

## 3. 供应链

`pnpm-workspace.yaml` / `.npmrc` 固定 exact-save、time-based resolution 和至少 24 小时（1,440 分钟）的新版本冷却期。`verify-lockfile` 会 fail-closed 核对：

- 所有直接 registry 依赖使用 exact 或受 exact catalog 管理；
- workspace 依赖只使用允许的 `workspace:` 形式；
- 禁止 git、HTTP tarball、`file:`、`link:` 等不可审查 direct source；
- 根 `packageManager`、lockfile importer 与 manifest/catalog 不漂移；
- lifecycle build 仍只允许显式 `allowBuilds` 项。

当前 `overrides.lodash-es` 精确固定为 `4.18.1`，用于消除已审计到的 high advisory；它不是 advisory ignore，也不能放宽为 range。冷却期的 bootstrap 例外也只能写成精确的 `name@version`，过期后应移除。

`pnpm audit --audit-level=high` 不使用 registry-error/unfixable 忽略参数；注册表不可达或发现 high/critical 都让 CI 失败。24 小时冷却是新增解析策略，不会自动证明旧 lockfile 安全，因此 audit 与 lockfile guard 都不可省略。

## 4. 发布边界

当前全部 workspace 包都是 `private`。G-22 不发布 npm 包，而是在匹配 `v<package.json version>` 的 tag 上执行完整门禁。`pnpm release:check` 只校验形状；`pnpm release:bundle` 生成：

- `_tmp_release/bundle/`：只包含已发现 workspace package 的已编译 `dist` 与明确列出的根文档；
- README、许可证、NOTICE 与 CHANGELOG；
- `_tmp_release/release-manifest.json`（`tracegraph.release-manifest.v1`）：按规范化相对路径排序，记录每个文件字节数和 SHA-256，并声明 `bundle_root: "bundle"` 与 `distribution_mode: "private-workspace-build-artifact"`。

staging 会复制清单中的每个文件并在目标上重新核对字节数与 SHA-256；未注册的 rogue `dist` 不会进入清单或 bundle，release workflow 上传该 bundle 与清单，并随 P8 增加独立 preview archive/checksums 和三条演示证据包（见第 6 节）。发布校验拒绝版本不一致、错误 tag、缺少 CHANGELOG 条目、声明的 bin/export 不是规范化 `./dist/` 路径或不存在、symlink、过大文件或越界路径。清单上限为 4,096 个文件、单文件 32 MiB、总量 256 MiB，序列化 manifest 另有 1 MiB 上限。它证明上传内容和构建出口，不等同于代码签名、容器镜像、npm provenance 或生产部署。

## 5. 文档纪律

不再维护覆盖全仓的手工 verification map 和独立 limitation map。每个 owning module 直接记录职责、代码、契约、边界与最窄验证入口；`implementation-consistency.eval.ts` 核对公开契约、事件、版本和路由是否仍能回到对应模块文档。TraceGraph 遗留边界及其 V2 去向集中在 `docs/outlive-agent-v2/10-tracegraph-to-outlive-migration/README.md`，G-22 文档 eval 核对迁移表和模块索引结构。

双语采用“一个详细技术事实源 + 两个入口”：中文 README/模块文档是完整说明，`README.en.md` 提供可运行的英文启动、验证、发布和安全边界；`docs/README.md` 同时索引二者，避免复制整套模块文档后长期漂移。

## 6. P8 可执行证明与 preview 安装

标签触发的 release workflow 已接入三条证明与 preview 构建/上传路径；本轮只验证本地等价命令，没有创建 tag、推送或远端 CI 成功声明。

`node demos/proofs.mjs` 在新建隔离目录运行 DEMO-080/081/082，保留 canonical
JSONL、投影、真实文件、oracle 与 SHA256SUMS。受控的是模型决策和公开合成
内容；SIGKILL、WAL 对账、MemoryUse、Capsule 校验、run_test 子进程组和
durable cancel 都走真实实现。恢复 oracle 同时验证重复对账不增加事实或
再次修改文件；取消 oracle 验证 leader、descendant 与整个 POSIX 进程组都不存在。

`node scripts/create-preview-release.mjs` 在既有 release gate 通过后创建私有
preview tar.gz，增加 manifests、frozen lock/config、安装/冒烟/演示脚本、明确
局限、逐文件/归档 SHA-256 与 CycloneDX 1.6 依赖清单。发布门现在检查 Desktop
main/preload/renderer 入口；Workbench CSS 经 build 复制到 dist，发布出口不再
指向缺失的 src。staging 重验构建输出，installer 校验 bytes 后执行
`pnpm install --frozen-lockfile --ignore-scripts --ignore-pnpmfile`，`--desktop`
才显式下载 Electron。初次安装拒绝所有未登记文件/目录；安装后校验只额外允许
根目录与已登记 package 根的真实 node_modules，不能夹带 hook/config/新包。
若已装 CLI，再以 `--desktop-runtime` 单独下载 Electron，不重跑 pnpm。

当前兼容归档的安装冒烟用解包目录中的 CLI 查询认证私有共享 Host，再核对
同一 Host 的 loopback HTTP Session 视图；旧 Desktop Host 独立进程/framed RPC
保留额外兼容验证，不能据此描述当前 Desktop 的连接架构。它使用 ESM import 条件解析依赖，适配
Node 22.19 和 24；import-only 包无需增添 CommonJS 出口。tarball 不包含源码，
不能运行 build/dev/source-test；安装和启动命令见[发布文档](../releases/README.md)。

输出 SBOM 包含 lockfile 中 dev/optional registry 依赖和 workspace 包；另装
Node/pnpm/Electron native binary 与 OS 库不在完整清单范围。未提供签名、
notarization、auto-update 或 npm publication。clean-machine 与非维护者验收
必须保留真实环境和结果；本机新目录安装不能冒充这些证据。

最窄验证：`node --test scripts/verify-release.test.mjs scripts/create-preview-release.test.mjs`、
`node demos/proofs.mjs`，以及在新解包目录执行 `node scripts/preview-install.mjs`
与 `node scripts/preview-smoke.mjs`。篡改 dist 的负例必须在任何依赖安装前失败。
额外 `.pnpmfile.cjs` / workspace package / config 文件的负例也必须失败；
Host 或 Runtime 清理失败时不能写入或输出 passed 报告。

## 7. 自包含安装包与当前恢复验收

当前正常安装入口由 [build-desktop-product.mjs](../../scripts/build-desktop-product.mjs)
生成 macOS DMG/ZIP 与 Windows per-user NSIS EXE/ZIP。安装包携带 Electron、
独立 Node 24.21.0、已编译 Web/CLI/Host、项目模板与目标平台原生依赖；用户
无需外部 Node、pnpm 或终端即可启动和配置模型。仅源码构建机器需要仓库
固定版本的工具链。与第 6 节历史 workspace preview tarball 的依赖安装步骤区分。

```bash
env -u NODE_OPTIONS pnpm build
env -u NODE_OPTIONS pnpm dist:desktop --output /tmp/outlive-desktop-product
env -u NODE_OPTIONS node scripts/smoke-desktop-product.mjs \
  --product /tmp/outlive-desktop-product --output /tmp/outlive-desktop-smoke
```

构建目录必须新建。独立 Node 来自固定官方归档并核对官方 SHA-256；平台
node-pty/TypeScript 原生文件核对目标格式。TypeScript 标准库 `.d.ts` 是实际
运行资源，不能按应用声明文件统一删除；真实安装候选曾因缺失这些文件失败，
该负例保留，不转写为通过。品牌资源在 staging 前从唯一 vector 来源校验。
每次构建记录 `product-release.json`、`stage/stage-inventory.json`、
`packaged-inventory.json` 和 `artifacts/SHA256SUMS`，分别约束组合来源、staging、
交付资源与容器字节。目标原生冒烟使用固定 bundled Node 和真实 CodeGraph，
