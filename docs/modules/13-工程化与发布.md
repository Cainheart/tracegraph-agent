# 模块 13：工程化与发布

> 定位：G-22 的可执行质量门、供应链约束与私有 workspace 发布纪律。  
> 入口：`.github/workflows/`、`vitest.coverage.config.ts`、`scripts/`  
> 最后核对：2026-09-19

## 1. 本地与 CI 命令

```bash
pnpm verify:lockfile
pnpm supply-chain:check
pnpm typecheck
pnpm test
pnpm test:e2e
pnpm coverage
pnpm evals
pnpm release:check
pnpm release:bundle
```

`pnpm build` 的第一步是 `pnpm clean:dist`。清理器只接受 `apps/*`、`packages/*` 下具有安全 `package.json` 的 manifest-owned `dist`，拒绝 symlink，并且不会清理任意匹配名称或仓库外目录。这样发布校验读取的是本次构建产物，而不是历史构建残留；`clean-dist.test.mjs` 用 rogue 目录和 symlink 反例锁定该边界。

CI 固定为三个互相独立的 job：

| Job | 必须成功的边界 |
|---|---|
| `typecheck` | frozen install、lockfile guard、先 clean build 再做全包/评测类型检查、release shape；不依赖旧 `dist/*.d.ts` |
| `test` | high/critical audit、unit/integration、CLI E2E、覆盖率门、coverage artifact |
| `evals` | 清空 provider/OTLP 凭据后运行 G-16 离线评测并上传 bounded report |

三个 job 的安装顺序固定为：`pnpm/setup install:false` → 直接执行 `node scripts/verify-lockfile.mjs --skip-frozen` → `pnpm install --frozen-lockfile` → 完整 lockfile/测试门。预安装阶段刻意不经 `pnpm <script>` 分派，避免任何宿主脚本包装器先做隐式安装；manifest/config 级的 direct source、range、override 与 pnpm pin 问题会在依赖 lifecycle script 有机会运行前失败。安装后的 `verify:lockfile` 再做 frozen drift 核验。

工作流仅授予 `contents: read`，checkout 不持久化凭据；第三方 Actions 使用完整 commit SHA，pnpm 与 Node 使用精确版本。PR 不能通过修改浮动 tag 在下一次运行时悄悄更换 Action 实现。仓库内可验证工作流结构及同构本地命令，但当前没有可引用的 GitHub-hosted run URL，因此不能把“workflow 已定义/本地已通过”写成“远端 CI 已成功运行”。

## 2. 覆盖率门

`pnpm coverage` 先产生 V8 JSON summary，再由仓库脚本独立核对：

- 全局 line coverage 不低于 70%；
- `packages/contracts/src/**` 聚合 line coverage 不低于 90%；
- `packages/core/src/context.ts` 与 `packages/core/src/policy*.ts` 聚合 line coverage 不低于 90%。

校验器拒绝缺失、空、越界、非有限或路径逃逸的 coverage 输入。专用失败注入测试会人为降低命中数，证明阈值并非只写在配置中而没有执行。

## 3. 供应链

`pnpm-workspace.yaml` / `.npmrc` 固定 exact-save、time-based resolution 和至少 24 小时（1,440 分钟）的新版本冷却期。`verify-lockfile` 会 fail-closed 核对：

- 所有直接 registry 依赖使用 exact 或受 exact catalog 管理；
- workspace 依赖只使用允许的 `workspace:` 形式；
- 禁止 git、HTTP tarball、`file:`、`link:` 等不可审查 direct source；
- 根 `packageManager`、lockfile importer 与 manifest/catalog 不漂移；
- lifecycle build 仍只允许显式 `allowBuilds` 项。

当前 `overrides.lodash-es` 精确固定为 `4.18.1`，用于消除已审计到的 high advisory；它不是 advisory ignore，也不能放宽为 range。冷却期的 bootstrap 例外也只能写成精确的 `name@version`，过期后应移除。

`pnpm audit --audit-level=high` 不使用 registry-error/unfixable 忽略参数；注册表不可达或发现 high/critical 都让 CI 失败。24 小时冷却是新增解析策略，不会自动证明旧 lockfile 安全，因此 audit 与 lockfile guard 都不可省略。

## 4. 发布边界

当前全部 workspace 包都是 `private`。G-22 不发布 npm 包，而是在匹配 `v<package.json version>` 的 tag 上执行完整门禁。`pnpm release:check` 只校验形状；`pnpm release:bundle` 生成：

- `_tmp_release/bundle/`：只包含已发现 workspace package 的已编译 `dist` 与明确列出的根文档；
- README、许可证、NOTICE 与 CHANGELOG；
- `_tmp_release/release-manifest.json`（`tracegraph.release-manifest.v1`）：按规范化相对路径排序，记录每个文件字节数和 SHA-256，并声明 `bundle_root: "bundle"` 与 `distribution_mode: "private-workspace-build-artifact"`。

staging 会复制清单中的每个文件并在目标上重新核对字节数与 SHA-256；未注册的 rogue `dist` 不会进入清单或 bundle，release workflow 也只上传该 bundle 与清单。发布校验拒绝版本不一致、错误 tag、缺少 CHANGELOG 条目、声明的 bin/export 不是规范化 `./dist/` 路径或不存在、symlink、过大文件或越界路径。清单上限为 4,096 个文件、单文件 32 MiB、总量 256 MiB，序列化 manifest 另有 1 MiB 上限。它证明上传内容和构建出口，不等同于代码签名、容器镜像、npm provenance 或生产部署。

## 5. 文档纪律

不再维护覆盖全仓的手工 verification map 和独立 limitation map。每个 owning module 直接记录职责、代码、契约、边界与最窄验证入口；`implementation-consistency.eval.ts` 核对公开契约、事件、版本和路由是否仍能回到对应模块文档。TraceGraph 遗留边界及其 V2 去向集中在 `docs/outlive-agent-v2/10-tracegraph-to-outlive-migration.md`，G-22 文档 eval 核对迁移表和模块索引结构。

双语采用“一个详细技术事实源 + 两个入口”：中文 README/模块文档是完整说明，`README.en.md` 提供可运行的英文启动、验证、发布和安全边界；`docs/README.md` 同时索引二者，避免复制整套模块文档后长期漂移。
