## 2. 资源上界

| 字段 | 默认 | 天花板 | 实际生效于 |
|---|---|---|---|
| `maxFileBytes` | 64 KiB | 1 MiB | `read_file`、`search` |
| `maxFiles` | 2 000 | 10 000 | `search` |
| `maxBytes` | 8 MiB | 64 MiB | `search` |
| `maxDepth` | 16 | 64 | **仅 `search`** |
| `deadlineMs` | 5 000 ms | 60 000 ms | `read_file`、`list_dir`、`search` |
| `maxMatches` | 50 | 1 000 | `list_dir`、`search` |

`normalizeFileToolLimits()` 逐项校验 safe integer、下限（`maxDepth` 为 0，其余为 1）与天花板，否则 `RangeError`。

`read_artifact` 不使用这组 Workspace 文件遍历 limits：Runtime-only Artifact reader 有独立 8 MiB 单工件硬上限，而每个工具 Observation 只返回最多 4,000 字节。公开 Host/Web Artifact 路径仍是 1 MiB，且没有因此获得通用 internal route。

### 2.1 G-05 输出契约与统一执行边界

每个 Tool 的 input/output 都先从 Zod 转换为 `packages/contracts/src/tool.ts` 定义的 bounded local JSON Schema：根必须是 object，单份最多 64 KiB、深度 8、节点 256、属性 64，不解析远程 `$ref`。`executeToolDefinition()` 的固定顺序是：深冻结已解析参数 → 合并父级 AbortSignal 与 per-tool timeout → executor → output schema 校验 → `render()` → `RawToolResultSchema` 再校验 → 按 UTF-8 字节裁剪最终 envelope。

`packages/core/src/tool-output-limits.ts` 集中声明十九个工具的 summary/content/facts 与完整结果上限，并把 G-02 默认 spill 阈值也作为同一常量导出。output schema 不匹配会在 render、Artifact 与 Ledger 之前变成 `output_contract_violation`，不会把脏数据写入；executor/renderer 异常统一为不暴露异常正文的 `internal`。

失败保留两层语义：Receipt `code` 以及 Receipt metadata / tool Event 的 `business_code` 是工具领域原因（如 `tests_failed`、`stale_base`）；Receipt metadata 的 `failure_code`、`tool.failed.data.code` 与 batch result 的 `failure_code` 则只取 `invalid_arguments/timeout/output_contract_violation/denied/internal`。控制流/UI 使用后一层，诊断不能丢弃前一层。

## 3. 决策期双层闸门：Tool contract + G-06 PolicyEngine

Runtime 先用 `validateToolCall(..., policyPrevalidated:true)` 完成 ToolCall、注册表与 strict input schema 校验，再把已验证工具的 capability、side effect、mode 与参数中的逻辑 path/diff size 交给 `PolicyEngine`。不再把散落在 Tool Registry 的 legacy sandbox/approval 判断当作主策略源；旧调用方若不传 `policyPrevalidated`，原有 capability/plan/read-only/requiresApproval 防线仍保留为兼容路径。

G-06 的求值顺序是安全语义的一部分：

| 顺序 | 检查/选择 | 结果 |
|---|---|---|
| 1 | Workspace capability；`read_artifact/list_artifacts` 仅为 current-Run Artifact 例外 | false ⇒ hard deny，规则不能覆盖 |
| 2 | plan mode 只放行可信只读规划白名单；`todo_write` 还必须保持 `side_effect:none` | hard deny |
| 3 | preset `allowed_tools`、`read-only` 禁 write、`path_scope` 与非法逻辑 path | hard deny |
| 4 | Host rules：`priority` 降序；同优先级 `deny > ask > allow > rule_id` | 首个匹配；`tool/side_effect/path_glob/max_diff_lines/session_tags` 是合取 |
| 5 | 无 Host rule 时按 preset `approval_policy` 取默认 allow/ask | `workspace-write` 的 write 为 ask；`full-write` 为 allow |
| 6 | 独立 project rules 层只找 `ask/deny` | 只能把 Host 结果收紧，project allow 在契约/loader 即被拒绝 |
| 7 | 记录 `policy.evaluated`；deny 再记录 `policy.denied` | 决策包含 source、rule id/priority、explanation、policy/action digest |

`path_glob` 只匹配规范化的 workspace-relative 逻辑路径。它把越界/非法字面量提前 fail-closed，但**不代替**第 4 节的 realpath/symlink containment 与敏感文件执行时复核。两个 Artifact 例外也不是 Workspace 提权：Plain Chat 可以列当前 Run 的公开 metadata，并分页回读自己因压缩生成的 Context archive，但不能用它们打开任意路径、任意 Artifact content 或其它 Run 的 locator。

一般 `ValidatedAction` 带 `workspace_handle_id`；经批准的新写入使用 `ApprovalBoundValidatedAction`，还必须带 `approval_id`、`approval_token_id`、`action_digest` 与 `policy_digest`。这把“哪个工作区、哪份策略、哪次批准、哪个具体动作”固化成一个不可混用的动作记录。

## 4. 三层路径防线

| 层 | 位置 | 作用 |
|---|---|---|
| 契约层 | `RelativePathSchema` | 拒绝绝对路径、盘符、`..` 段 |
| 解析层 | `resolveWorkspacePath()` / `assertInside()` | `realpath` 解析后确认仍在 `real_root` 内 |
| 执行层 | `isSensitiveWorkspacePath()` | 按路径段命中凭据文件名清单 |

`workspace.test.ts` 的两个用例正好守住前两层：**拒绝目录穿越与绝对路径访问**、**拒绝解析到工作区根之外的符号链接**。

### 敏感路径清单

命中的段：`.env`、`.aws`、`.gnupg`、`.netrc`、`.npmrc`、`.ssh`、`credentials`、`credentials.json`、`id_rsa`、`id_ed25519`，以及 `.env.*` 前缀与 `.pem` / `.key` / `.p12` / `.pfx` 后缀。

## 5. `read_file` / `list_dir` / `search`

**`read_file`**：`readBoundedUtf8()` 打开文件后 `Buffer.allocUnsafe(maxBytes + 1)`、**单次 `handle.read()`**，取 `min(bytesRead, maxBytes)`，`truncated = bytesRead > maxBytes`。注释明确"不做完整 materialize"。facts 里带 `content_excerpt`（这是模块 03 里享受压缩豁免的那个字段）。超限、超时、abort 分别有独立错误码，超时/abort 时 facts 仍带 `content_excerpt` 与 `bytes_read`。

**`list_dir`**：递归遍历，`depth` 由入参控制（0..3），每层排序用 `localeCompare`，总条目数受 `maxMatches` 限制（**目录也会消耗配额**），受 `deadlineMs` 限制，超限时置 `incomplete` 并给出 `limit_reasons`。

**`search`**：遍历文件 → 检查忽略与敏感 → 记录 `limitReasons`（`deadline` / `max_files` / `max_bytes` / `max_matches` / `max_depth` / `max_file_bytes`）→ 逐行 `line.includes(pattern)` 匹配，命中行截断到 500 字符。读失败的文件**静默跳过**（注释理由：编辑器的并发改动、不可读文件、设备文件都很常见，不该让一次搜索整体失败）。

匹配是**子串比较，不是正则**，且大小写敏感。

### 5.1 `read_artifact`：当前 Run 的有界 archive 回读

`read_artifact` 只接受 `artifact:<artifact_id>` opaque locator。Runtime 从正在执行的 `RunState` 注入 project/run 身份，调用 `ArtifactStore.getInternal()`，然后再次检查 kind 只能是 `spilled_tool_output` 或 `context_source_archive`；因此模型不能在参数中自选 scope。Artifact metadata、8 MiB 总长度、hash 与二次脱敏校验仍全部执行。

读取从 `offset:0` 开始，返回 `bytes_read / total_bytes / truncated / next_offset?`；后续必须使用前一页的 `next_offset`，偏移还必须落在 UTF-8 字符边界。成功后 Runtime 发 `context.spill_refetched`，事件只含 locator/hash/range 和 ArtifactRef；页内容继续以有界 Observation 进入下一轮，不复制进 Ledger。该 Observation 也被排除在再次 spill 之外，避免 locator 回读循环。

### 5.2 `list_artifacts`：发现当前 Run 的公开元数据

Runtime 注入的 callback 从当前 Run Ledger 的 `artifact_refs` 汇总并按 `created_at + artifact_id` 稳定排序；再次核对 project/run、去重且排除内部 `recovery_state`。工具返回 `artifact_id/locator/kind/content_hash/mime_type/byte_length/created_at`，只允许 offset 分页与 1..100 的 page limit，不返回 project/run 或内容正文。

成功的 listing 不再写成 `tool_output` Artifact，否则下一次 listing 会列出上一次 listing，形成自我增长。它只提供发现；真正读取仍必须经过专用工具，当前 `read_artifact` 只接受两种 G-02 Context archive。

### 5.3 `todo_read` / `todo_write`：Plan 的结构化工作集

`todo_read` 从当前 Run 的 canonical Ledger 重放 Todo，不接受模型提供的 project/run scope；按 item 分页返回稳定顺序，默认 25、最多 100 项。完整 page JSON 包含 `items/total/returned_count/offset/limit/last_sequence/truncated/next_offset?`；模型可见 Observation facts 则用 `todo_count` 表示同一个总数。专属 content/result envelope 上限是 512/640 KiB，Registry 还预留 headroom，并逐项检查两层 UTF-8 字节预算；因此最大 contract-valid Todo 可完整放进一项页，超单页列表则可少于请求 limit，但不会先被通用裁剪器截掉尾部。模型沿 `next_offset` 可读到合法 500 条上限中的最后一项。Observation 另保留按 UTF-8 边界截取的最多 4,000-byte content excerpt，完整 page JSON 进入 current-Run `spilled_tool_output` Artifact，可再用 `read_artifact` 分页回读。

`todo_write` 由 Runtime 注入 scope 与 actor，只接受 create/update 输入，并把状态迁移记录成 `todo.created|updated|completed|blocked` 四类 strict Event。它虽然不修改 Workspace、声明 `side_effect: "none"`，但为避免依赖图写竞争而标记 `concurrency_safe:false`。

写入前会校验最多 500 条、id 唯一、依赖存在、无自依赖与无环；校验失败不得先 append 再报错。模型完成 Todo 时必须引用同 Run、先于当前 mutation 的 eligible 独立成功执行事实：三重成功且非 `todo_read/todo_write` 的 `tool.completed`、带严格成功 `run_test` Receipt 的 `test.completed`，以及 `action.verified/reconciled`、`patch.preview_created/applied`、`graph.snapshot_created/delta_created`。Todo/Plan/Model/Policy/Approval/lifecycle Event 即使已经存在也以 `evidence_event_not_eligible` 拒绝；已有证据的 done Todo 在保持 done 时不能清空。用户完成由本次 actor-bound Todo Event 确认该 Todo，但它不能给另一个模型 Todo 自证。这是“durable execution fact 已发生”的门，不是逐 Todo 语义验收器。等待 Plan 批准时的 Todo 变更会刷新 `plan.ready` revision，使旧批准请求失效；终态、`interrupted` 与 `needs_manual_review` 禁止新 Todo 写入。

### 5.4 G-07 子 Agent 控制工具

`spawn_subagent` 不接受 provider key、role prompt 或 tool allowlist；这些 authority 只能由 Host-owned `SubagentRegistry` 从 `profile_name` 解析。Runtime 再取请求预算与 profile ceiling 的有效交集，将 provider、role hash、allowlist、depth、budget 冻结到 `SubagentSpec`。child 本身调用 Tool 时还要通过 G-06 hard constraint；不在冻结 allowlist 的调用以 `policy.denied{reason:"subagent_tool_allowlist"}` 在 `tool.started` 前收口。

`send_subagent_message` 与 `interrupt_subagent` 只能找到当前父 Run 的 direct active child，不接受模型伪造 project/run/actor；内部消息使用 `parent_agent`，浏览器 steering request 仍无 actor 字段。`list_subagents` 只从父 canonical Projection 读冻结 spec/link/status，不直接扫进程内 Map。四个工具在 Plan Mode 都被 Runtime 拒绝；父子委派只在 execute 控制面成立。

当前 spawn 的 Tool Promise 同步等待 child terminal；这不是任意父模型轮次可续聊的 Team scheduler。child terminal 已 durable 但父 receipt 持续写失败时，Runtime fail-stop 并保留 permit，由 Host restart reconciliation 补回执；它不在同进程盲重试启动 child。

## 6. Patch 两阶段流程

### 6.1 `preview_patch`（不落盘）

1. abort → 敏感路径
2. `resolvePatchTarget()`：目标存在则 `realpath`；不存在则解析父目录并在根内确认，返回候选新文件路径
3. 读 `before`（不存在则 `""`）
4. 锚点结构检查：不存在但 `expected` 非空 → `patch_target_missing`；存在但 `expected` 为空 → `patch_anchor_empty`
5. `occurrences = before.split(expected).length - 1`，**必须恰好为 1**，否则 `patch_anchor_mismatch`
6. 计算 `after` 与 diff
7. **敏感内容闸门**：

```339:345:packages/core/src/tool-registry.ts
    if (redactSensitiveText(diff) !== diff) {
      return {
        status: "failure",
        code: "patch_sensitive_content",
        summary: "Patch preview contains sensitive or local-path content that cannot be shown exactly",
      };
    }
```

8. 成功时返回 `base_hash = sha256(before)`、`patch_hash = sha256(after)`、`scope = [path]`

第 7 步是本模块最保守的设计：**diff 里只要出现任何会被脱敏的内容（机密或本机路径），整个预览直接失败**，而不是"脱敏后展示"——因为它无法被精确展示，而不精确的 diff 不能作为审批依据。

第 8 步的两个哈希是后续审批与提交的钥匙：`base_hash` 锁定改动前的文件状态，`patch_hash` 锁定改动后的内容。

### 6.2 `commit_patch`（受策略与完整性边界保护）

Runtime 不允许模型直接调用 `commit_patch`；成功 preview 后才由 Host 构造 commit call、解析 canonical target，并计算稳定 `action_digest`。digest 绑定 project/run/action/tool、workspace handle、policy digest、规范化 arguments/path、canonical target hash、base/patch hash 与 scope：授权后任一要素变化都会在改盘前被拒绝。

三档 preset 对同一 preview 的分支：

| preset | commit policy | Runtime 行为 |
|---|---|---|
| `read-only` | hard deny | preview 后立即写 `policy.evaluated` + `policy.denied` 并失败；不创建 `approval.requested` |
| `workspace-write` | ask | 保存完整绑定 pending approval，等待 Web/SDK 的 `approve/reject` 命令 |
| `full-write` | allow | 不询问用户，不创建 `approval.requested` / `approval.granted`，也不签发/消费 token；重算 canonical action digest 后直接进入 commit/WAL 链 |

只有最终 policy 为 `ask` 时才进入批准/token 分支。批准时 `ApprovalTokenStore` 精确校验 approval/project/run/action、action/policy digest、scope 与 expiry；consume 会先从 Map 移除再检查，因此失配、过期或并发重放都不能留下第二次尝试机会。新 `ApprovalBoundGrant` 把 token id 与全部 digest/scope/base/patch 绑定写入 `approval.granted`。token 是进程内 opaque capability；待审批恢复不会复活旧 token，只按 recovery state 中冻结的 effective policy 重新签发。policy `allow` 不伪造审批事实或 token。

在真正记录 `tool.started` 前，Runtime 会再用该 Run 冻结的 effective policy 重评一次执行输入。若最终变为 `deny`，立即写入 `policy.denied` 并以 `capability_denied` 失败，不会产生 `tool.started`、WAL 或 mutation；若最终为 `ask`，则必须有 `approved-once` 绑定，`policy-allow` 不能冒充已批准。

| 顺序 | 检查 | 失败码 |
|---|---|---|
| 1 | abort → 敏感路径 | `tool_aborted` / `sensitive_file_blocked` |
| 2 | 读 `before` | — |
| 3 | **`sha256(before) !== base_hash`** | `stale_base` |
| 4 | 锚点结构是否变化 | `patch_anchor_empty` / `patch_target_missing` |
| 5 | 锚点唯一性 | `patch_anchor_mismatch` |
| 6 | **`sha256(after) !== patch_hash`** | `patch_hash_mismatch` |
| 7 | 调用 Runtime 注入的 `patchMutation.prepare`：再次比较当前 canonical absolute target digest；匹配后才把精确 before-image + `prepare` WAL durable | target 变化为 `action_digest_mismatch` 且 WAL 仍为空；Action WAL 错误向上抛出，不能伪装为普通 Tool failure |
| 8 | 以随机名 `wx` 创建同目录临时文件，写入 after bytes 并 file fsync | — |
| 9 | 写后若被 abort → 删临时文件 | `tool_aborted` |
| 10 | **`rename(temporary, path)` + parent directory fsync** | — |
| 11 | 重新读取实际文件并核对 after hash，调用 lifecycle 落 `applied` | 不一致则中断提交闭环，留给启动对账 |
| 12 | 返回 `patch_committed`；Runtime 再写 Receipt/Event 与 committed/verified phase | — |

核心语义：**授权的是“某个 Run、某份 policy 下，某一个 canonical target 与哈希对的具体改动”，不是“允许修改这个文件”**。文件在授权后被任何方式改动，第 3 步就会失败；参数/目标/scope/policy 被替换会在 action digest、ask 路径的 token binding 或 mutation-boundary target 校验中失败。

第 8–10 步用“同目录随机临时文件 + `wx` + file fsync + `rename` + directory fsync”实现 durable 原子替换。`wx` 只防临时文件名碰撞，**不是目标文件的跨进程锁**；其它进程仍可能在检查和 rename 前后改动目标。Runtime 会在 rename 后重读 after bytes，并用 Action WAL 把 rename 与后续 Event/Receipt 对账。

### 6.3 非 Patch `ask` 的 fail-closed answerer

项目/Host rule 可以把 read 或 execute Tool 收紧为 `ask`。这条路径使用 Host 注入的 `approvalAnswerer`，不是 Web 的 Patch 审批条；request 已带 action/policy digest、project/run/action、scope、expiry 与 explanation。只有 strict `allowed-once` 会签发并原子消费 token 后继续；answerer 缺失、抛错、返回非法值，或返回 `rejected/cancelled/unavailable`，都会写 `approval.denied` 并失败。Web/SDK 的手工 `approve/reject` 只用于 pending Patch，不能回答一般 Tool ask。

## 7. `run_test`、`SandboxRunner` 与 bounded process

固定参数：入口 `test/run.mjs`、`cwd = workspace.real_root`、可执行文件 `process.execPath`、超时 **15 000 ms**、输出上限 **64 000 字节**。Runtime 把本 Run 冻结 permission preset 的 `sandbox_mode` 与 Host-owned `sandboxRunner` 注入 Tool context；工具不能从模型参数选择二者。

结果编码的判定优先级（顺序即语义）：

```
aborted        → tool_aborted
timedOut       → timeout
truncated      → test_output_limit
sandbox 未生效 → sandbox_unavailable（started:false）
exitCode === 0 → tests_passed
否则            → tests_failed
```

`NativeSandboxRunner` 先 canonicalize workspace/cwd/executable 并拒绝 cwd symlink escape。macOS restricted mode 只有可信 `/usr/bin/sandbox-exec` capability probe 得到 `full` 才启动：`read-only` 禁写，`workspace-write` 只允许 workspace 内写，二者都禁网。Linux 当前只探测固定 bwrap 路径但未启用 runner，Windows 也没有 backend；两者与缺失/失败的 Seatbelt 都返回 `none + unmet_constraints`，restricted child 不启动。`danger-full-access` 明确报告 `none` 后直跑。

底层 `runBoundedProcess()` 的边界：

- **环境变量白名单**：只注入 `PATH` 与 `NODE_ENV=test`
- `shell: false`（不经 shell，无注入面）
- POSIX 下 `detached: true` → **独立进程组**，终止时 `process.kill(-pid, signal)`
- 终止采用**两段式**：先 `SIGTERM`，**250 ms** 后升级 `SIGKILL`
- timeout 与 abort 走**同一条终止路径**（因此不存在"abort 不杀进程"的情况）
- 输出超限时主动终止子进程（`terminate("output")`），而不是继续读

结果 facts 永远带 `started` 与 strict `sandbox_report`。Runtime 再校验 mode/report，并把报告复制到 Receipt metadata、Observation facts、Tool Event 和 `test.completed`；不可验证时强制改成 `sandbox_unavailable`。该 code 的通用 failure class 是 `denied`，用来区分“策略没有允许启动”与“测试代码已启动但失败”。

`process.test.ts` 覆盖上述 process 行为：**超时子进程拒绝退出时从 SIGTERM 升级到 SIGKILL**、**输出封顶并终止忽略 SIGTERM 的子进程**、**传播 AbortSignal 并报告停止原因**，以及 POSIX 下回收 grandchildren、Tool 外层 timeout 复用同一进程组清理。`sandbox/sandbox.test.ts` 覆盖 profile/参数注入、missing backend 不执行、内置 Node fixture、danger 直跑、Linux/Windows 诚实报告、禁写/禁网、symlink/path 防逃逸。

### 7.1 批调度、timeout 与取消边界

显式 `tool_calls` 最多 16 项。Runtime 在任何成员开始前预校验完整批次，再把 `concurrencySafe && sideEffect !== "write"` 且无需审批的连续区间切为安全波，默认每波最多 4 个；write、requiresApproval 与 `concurrencySafe:false` 调用逐个串行。工具体可以并发，但 start/completion Event、Observation 与 batch result 都按请求顺序写入；一个失败波会等已启动成员全部 settle，成功 preview 则形成审批 barrier。

通用 timeout 用 `AbortSignal.timeout()` 与 `Promise.race` 保证 Runtime 及时返回 `timeout`，并把 signal 交给 executor；这不是任意资源的强制终止，忽略 signal 的第三方 executor 可能后台继续。`commit_patch` 另有 Host-only cancellation shield：WAL prepare 后仍做一次最终 signal check，随后在原子 rename 前同步 arm；此后 stop/timeout 不能抢先返回，而要等 applied WAL、Receipt、`patch.applied` 与 `action.verified` 收口，Host durability error 也必须优先透传。内置 `run_test` 是有进程边界的另一特例，使用上一节的 process-group 回收。批 scheduler 也只存在于当前 Runtime，没有跨进程 lock。

## 8. 不变量

1. Workspace 工具只能作用于 `WorkspaceHandle` 声明的工作区内，且能力必须为 `true`；`read_artifact` / `list_artifacts` 不接触 Workspace，只能作用于 Runtime 绑定的当前 Run Artifact scope。
2. `readonly_local` 工作区的四个写/执行能力必须为 `false`（契约层 `superRefine` 强制）。
3. 敏感路径一律拒绝，不做脱敏返回。
4. 锚点必须唯一命中（`occurrences === 1`）。
5. 提交前 `base_hash` 与 `patch_hash` 都必须与预览时一致。
6. 文件写入必须先有 durable WAL `prepare`，再经“临时文件 + file fsync + `rename` + directory fsync”原子替换，并重读核对 after hash。
7. 子进程必定收到 SIGTERM，并在 250 ms 后收到 SIGKILL。
8. 子进程只能看到 `PATH` 与 `NODE_ENV`。
9. `read_artifact` 每页最多 4,000 字节，locator 不提供 project/run 输入；跨 Run、错误 kind、损坏 hash、非法 UTF-8 偏移均 fail-closed。
10. 模型只能看到 `name/description/input_schema`；output/timeout/concurrency/side-effect/limit/execute/render 均为 Host-only。
11. executor 输出必须在 render 前通过 output schema，render 后还要通过统一结果 schema 与 UTF-8 envelope 上限；失败数据不得进入 Artifact/Ledger。
12. batch 全量预校验先于第一个成员，只有安全非写调用能并行；durable 结果和 Observation 必须保持请求顺序。
13. restricted `run_test` 只有实际 sandbox report 可验证且 enforcement 可执行时才启动；报告必须进入 Receipt/Observation/Tool/Test durable 证据。
14. `commit_patch` 不经 SandboxRunner；`read-only` 在 preview 后、创建审批前拒绝 write，`workspace-write` 默认需手工批准并使用 one-shot token，`full-write` 不询问且不产生 approval/token；三者都保留 Workspace capability + action/policy digest + WAL 边界。
15. hard constraint 不可被 allow 规则覆盖；project policy 只允许 ask/deny，且恢复必须保留 Host/project 分层与原 policy digest。
16. token 的 scope/identity/digest/expiry 任一不匹配都拒绝并 burn，重复或并发消费最多一个成功。
17. 非 Patch `ask` 的 answerer 缺失、抛错、非法或 unavailable 一律 fail-closed；Patch ask 只由手工 approve/reject 继续。
18. 子 Agent 只能选 Host-owned profile；provider/role prompt/tool allowlist 不得出现在 model-facing input，child Tool 不在冻结 allowlist 时不得产生 `tool.started`。
19. spawn/send/list/interrupt 只能作用于当前 parent/direct-child 关系；模型和浏览器都不能伪造 `parent_agent` actor。
20. G-17 扩展 Tool 必须进入同一个 `ToolRegistry` 与执行管线；Run lease 冻结本次模型可见 Tool 集，活动 Run 期间不得 reload/deactivate 后偷换 schema。

## 10. 已知缺口与未完成分支

1. **Policy path 不是完整 filesystem 判定。** G-06 已把 capability/plan/preset、workspace-relative `path_glob` 与 max diff 提前到统一 `PolicyEngine`，但 policy 层不会 `realpath`，也不拥有敏感文件清单。`read_file` 读 `.env` 可能先得到 allow 的 `policy.evaluated`，随后仍在 `execute()` 以 `sensitive_file_blocked` 失败；这不是“已批准后越权”，而是执行边界更严格。真实路径/symlink containment 也必须在执行时复核，且外部进程仍能制造 check/use TOCTOU。

2. **`commit_patch` 仍没有跨进程 target lock。** G-06 已在批准时和 mutation boundary/WAL 前两次核对 canonical target digest，G-04 也已补 file/directory fsync、Action WAL、启动 hash 对账及默认关闭的显式 rollback；但 WAL 与 Tool 的队列仍只在单进程内串行，两个 Host 或外部编辑器可在后续 precondition、rename、重读之间竞争。检测到最终 hash 分歧时只能进入 `needs_manual_review`，不会自动覆盖。

3. **`preview_patch` 的敏感闸门会误伤正常文件。** 只要 diff 中出现任何本机路径字面量（例如文档里写了 `/Users/...`）或形似 token 的字符串，该文件就**永远无法被补丁**。这是有意的保守取舍，但会影响可用性，且错误信息不告诉用户"是哪个片段触发的"。

4. **`readBoundedUtf8` 单次 `read` 不保证读满。** 未循环填充到 `maxBytes`，理论上可能少读且不标记 `truncated`。常规文件系统下每次 `read` 通常返回请求量，但这是未防御的边界。

5. **`list_dir` 不使用 `limits.maxDepth`。** 它只用入参 `depth`（上限 3），而 `limits.maxDepth`（16）只有 `search` 用。但 `list_dir` 的 facts 会带上 `limits.max_depth = 16`，**展示值与实际生效值不符**，且 `max_depth` 永远不会出现在它的 `limit_reasons` 里。

6. **`list_dir` 的 `maxMatches` 配额被目录消耗。** 默认 50，一个宽目录只需 50 个条目就会触发 `incomplete`，而用户想看的文件可能还在后面。

7. **`search` 是子串匹配。** 不支持正则、不支持大小写忽略、不支持行号范围。契约里 `pattern` 只是 1..500 的字符串，因此工具描述若暗示"可写正则"就会误导模型。

8. **`run_test` 无需审批却会执行工作区内的脚本。** `requiresApproval: false`，但它运行的是目标仓库里的 `test/run.mjs`。默认 macOS `workspace-write` 会把文件范围限制在 workspace 并禁网，缺 restricted backend 时会 fail-closed；但脚本仍可改 workspace、消耗 CPU，显式 `danger-full-access` 更没有 OS 文件/网络隔离。这仍是能力模型里值得显式记录的一处不对称。

9. **`run_test` 只支持 `suite: "fixture"`。** 无法对真实仓库运行其原生测试命令（pnpm / pytest / gradle 等），因此"修复验证"在通用场景下缺一环。

10. **敏感文件名清单偏窄。** 缺少 `.git-credentials`、`.crt`、`id_ecdsa`、`.kube/config`、`.docker/config.json`、`.pgpass`、`*.jks` 等常见凭据位置。清单是硬编码的，扩展需要改代码而非配置。

11. **`FILE_TOOL_LIMIT_CEILINGS` 的校验对新增字段静默失效。** 实现是 `const maximum = FILE_TOOL_LIMIT_CEILINGS[name]`，若未来给 `FileToolLimits` 加了字段而忘记加天花板，`value > undefined` 恒为 `false`，该校验**静默通过**。

12. **`run_test` 的 `exitCode === null` 未被单独处理。** 进程被信号杀死时 `exitCode` 为 `null`，会落到 `tests_failed`，summary 显示 `exit null`——错误码丢失了"被信号杀死"这一关键信息。

13. **`preview_patch`、生产 Patch WAL 与 rollback 都只有单文件。** `PatchPreviewSchema.scope` 和 WAL target 虽是数组契约，但当前 Runtime 恒产生一个 target；显式 rollback 也拒绝多目标，不支持跨文件原子补丁或事务回滚。

14. **通用 timeout 是协作式取消。** Runtime 能按时结束等待并发出 AbortSignal，但无法强杀忽略 signal 的任意第三方 executor；`run_test` 的进程组逻辑是内置特例，不代表所有扩展工具都已资源隔离。

15. **批调度没有跨进程锁。** 安全波、写/审批 barrier 与 ordered append 只在一个 Runtime 内成立；两个 Host 仍可能竞争同一外部资源。G-13 的 OS boundary 只覆盖内置 `run_test` child，不把调度器、provider 或 Host 文件操作变成跨进程隔离。

16. **平台 sandbox 覆盖不完整。** Linux bwrap 只探测、不执行，Windows 无 backend；restricted mode 因此拒绝 `run_test`。macOS Seatbelt 依赖 Apple 私有 `/usr/bin/sandbox-exec` / `system.sb`，native runner 目前只产出 `full` 或 `none`，没有实际 `partial` 后端，也没有 Host 网络白名单代理。

17. **G-06 是单 Host 权限边界。** approval token 只在内存中，既不是签名 JWT 也不能跨进程恢复；CLI/env ceiling 需重启修改，用户选择只影响新 Run。没有远程主体/RBAC、签名 policy 分发、跨 Host revoke 或 target lock。`full-write` 明确关闭 child OS sandbox 且默认不询问写操作，必须只用于可信工作区。

18. **五个 G-08 Team 工具是 root-Ledger 协调面，不是跨 Host scheduler。** roster/mailbox/task board/heartbeat 已 durable，task mutation 以 optimistic version 保证单 Host 单 owner；但单个 spawn 仍同步等 child 终态，worker 并行只来自 G-05 batch + G-07 permit，也没有自动 heartbeat/sweep、旧 worker 自动重启、任务自动重派或跨 Host consensus。如果父 terminal receipt 持续落账失败，该进程会保留 permit 并 fail-stop，需 Host restart 后对账，而不是可用的同进程 retry loop。

19. **扩展 Tool 仍是进程内可信代码。** G-17 保证注册可逆、schema/权限路径一致与 Run surface 冻结，不会强杀忽略 signal 的第三方 executor，也不构成恶意 JavaScript 沙箱；标准 CLI 当前根本不加载任意第三方 module。
