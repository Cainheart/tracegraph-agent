## 2. 持久化与读取结构

```
写入：SessionEventProposal ──┐
                             ├─► JsonlEventLedger.append()  →  <dataDir>/events/<runId>.jsonl（逻辑 append-only + hash 链）
大载荷（diff/log/快照）──────┴─► ArtifactStore.put()       →  <dataDir>/artifacts/<artifactId>.data + .json
会话索引：Session header/event_ref ─► JsonlSessionStore     →  <sessionDir>/<projectHash>/*.jsonl
Patch 事务：ActionWal + exact before-image ────────────────►  <dataDir>/wal/
恢复尝试：RecoveryLedger ──────────────────────────────────►  <dataDir>/recovery/
旁路观测：已提交 SessionEvent ──► RuntimeTelemetryProjector ──► SafeTelemetry ──► noop/memory/OTLP-HTTP

读取：jsonl ──► projectRun() ──► RunProjection（wire 平面，已脱敏）
     工件  ──► ArtifactStore.get() ──► ArtifactWireResponse（三态，二次脱敏校验）

闸门：crypto.redactSensitiveText / redactStructuredValue / redactStructuredArtifactValue
```

一个关键分工：**账本只放 ID、引用和小型结构化事实，大对象放工件存储；Session 文件再只引用账本 Event**。当前 `EventTypeSchema` 有 102 种事件。事件里出现的是 `artifact_refs`、`patch_event_id`、`graph_delta_id`、`test_receipt_id` 这类指针，而不是 diff 正文。G-02 的 `spilled_tool_output/context_source_archive` 保存被替代的 Context 原文，Ledger 只留 locator/hash/压缩账目；G-03 的 provider usage/anomaly 是小型结构化事实，直接作为 `model.usage_reported` / `model.cost` / `model.usage_anomaly` 写 Ledger；G-05 的 `tool.batch_started/completed` 保存有序 action ids、并发计划/实测、序列化原因和逐项结果，但不复制工具原文；G-09 的 Plan revision 与 Todo 都是小型 canonical Event，成功 `todo_read` 的完整页在 512/640 KiB content/result envelope 内进入 `spilled_tool_output`，Observation 只保留最多 4,000 UTF-8-byte excerpt 与 locator，再沿用 G-02 `read_artifact` 回读；G-14 的运行中输入以 `user.input_queued/consumed` 小型事实进入 Ledger，未消费输入无需依赖进程内队列；G-21 的 Memory/Retrieval 事件只记录候选/命中/索引摘要和引用；G-07 只在父 Ledger 写 `started/message_sent/terminal` 有界回执与 child terminal hash，child 完整 timeline 留在独立 Ledger；G-18 的 PNG/JPEG/PDF 原始字节只存 Artifact，Ledger 只留 `AttachmentRef`、拒绝/抽取状态与 locator；G-17 只在 extension hook/Context 失败时写有界、非递归 `extension.error`；G-08 再把 roster/mailbox/task board/heartbeat/loss/sweep receipt 作为 13 种小型 root-Ledger 事实，G-12 追加 LSP diagnostics/unavailable 两种有界事实，G-20 追加有界 `code.intel_updated/stale_base_detected` 事实；projector v9 从同一账本重建 `team`、`attachments`、`subagents` 与可选 `code_intel`，没有第二份 Team/CodeIntel store；G-15 **不增加事件类型**，只在这些 canonical Event 成功提交后派生少量 Telemetry。G-01 的恢复上下文与精确待审批 Patch 属于内部 Artifact，而待批 Plan revision 直接从 Ledger 重放。G-04 的 before-image 必须保留未经公开脱敏的精确字节，因此单独进入私有 WAL backup，而不是 Artifact/Wire。

“只存引用”降低了两份 Event 正文漂移的表面积，但不等于原子双写：Runtime 先提交 Ledger，再追加 Session `event_ref`。若两步之间崩溃，以 Ledger 为准，Session 索引可能缺 ref。G-04 只会在恢复对应 Patch Action 时通过稳定幂等提案补齐相关引用，不会全量扫描并反向重建所有 Event ref。

## 3. `JsonlEventLedger`

### 3.1 存储形态

- 路径：`<root>/<runId 过滤非法字符>.jsonl`，**一个 Run 一个文件**
- 每行一个 `JSON.stringify(event)` + `\n`
- 语义为 append-only，但物理提交会重写“旧事件 + 新事件”的完整候选文件：同目录 `O_EXCL/O_NOFOLLOW` 临时文件（0600）→ write → file fsync → rename → directory fsync。崩溃后只能看到旧的完整版本或新的完整版本。

### 3.2 单写者串行化

```150:154:packages/core/src/event-ledger.ts
  #serialize<T>(operation: () => Promise<T>): Promise<T> {
    const result = this.#queue.then(operation, operation);
    this.#queue = result.then(() => undefined, () => undefined);
    return result;
  }
```

`#queue` 形成一条 Promise 链，保证同一进程内 append 串行。注意 `.then(operation, operation)` 把**失败分支也接到同一条链上**——上一次 append 抛错不会永久阻塞队列。`list()` 也会先 `await this.#queue`，因此具备「读己之写」语义。

### 3.3 append 的完整管线

1. `SessionEventProposalSchema.parse()` ——提案先过契约
2. 串行化排队
3. `#readList(run_id)` ——**读取该 Run 的全部历史事件**
4. **幂等短路**：若提案带 `idempotency_key`，且历史中存在同 key 事件 → **直接返回那条已有事件，不写入**
5. **终态守卫**（两段，见下）
6. 分配 `sequence = (previous?.sequence ?? 0) + 1`
7. 组装 body：所有 `undefined` 的可选字段用条件展开省略（不写 `"key": undefined`）
8. `previous_event_hash = previous.event_hash`（首条事件省略该字段）
9. `event_hash = sha256(stableStringify(body))`
10. `SessionEventSchema.parse({ ...body, event_hash })` ——**出站前再自校验一次**
11. 把完整候选 JSONL 写入私有临时文件并 file fsync，再 rename 覆盖 canonical 文件、directory fsync
12. 通知订阅者，**逐个 try/catch 且吞掉异常**

第 12 步的吞异常是刻意的，注释说明了理由：

> *Subscribers are projections/transport notifications, not part of the canonical commit. A faulty listener cannot roll back or make an already-durable append appear to have failed.*

即：**已经落盘的事件不允许因为一个 SSE 连接出问题而被报告为失败**。

### 3.4 同一 Run 的原子批次

`appendAtomic(scope, proposals, finalize?)` 在同一 project / Run / Session 上先内存 stage 整个 hash-chain tail。每条 proposal 都按单条 append 的幂等、终态与 schema 不变量解析为确定 Event；可选 `finalize` 再从这批**已解析的 Event id**构造最终 receipt。任一 proposal / receipt 校验失败、幂等冲突或 durable replace 失败，都不会让新 tail 或其通知对读者可见。

整批事件仅执行一次“完整候选 JSONL → 私有临时文件 → file fsync → rename → directory fsync”；成功后才按顺序通知 listener。G-08 用它提交 `team.created + late-create backfill joins`、`subagent.started + team.member_joined` 以及“本次 sweep 的全部 `team.member_lost` + `team.sweep_completed`”。空 sweep 也会以只有 receipt 的原子批次落盘。

这个原子性严格限于**一份 root Run JSONL 的一次 durable replace**；它不覆盖 child Ledger、Session 引用、Artifact/WAL、Workspace 文件、外部系统或另一台 Host。

### 3.5 终态不变量

实现先拒绝第二个 terminal Event；若 Run 已有终态，则再按显式白名单检查后续事实。

语义：**一个 Run 只能有一个终态事件**。终态后只允许不会重新启动模型/工具的维护事实：`action.late_ignored`、G-04 的 `action.reconciled/diverged/rollback_refused/verified` 与 `patch.rolled_back`，以及 `session.*` 生命周期事实。它们可以补审计或显式撤销 Patch，但不能写第二个 Run 终态。

### 3.6 读取时的六道校验

`#readList()` 在读取阶段重建全部完整性保证：

| 顺序 | 检查 | 失败时 |
|---|---|---|
| 1 | 文件不以 `\n` 结尾 | `LedgerCorruptionError("partial trailing JSONL record")` |
| 2 | 每行能通过 `SessionEventSchema.parse` | `LedgerCorruptionError("invalid event schema")` |
| 3 | `sha256(stableStringify(body)) === event_hash` | `LedgerCorruptionError("event hash mismatch at sequence N")` |
| 4 | `sequence` 严格递增且步长为 1 | `LedgerCorruptionError("non-monotonic sequence N")` |
| 5 | `previous_event_hash === 上一条的 event_hash` | `LedgerCorruptionError("broken hash chain at sequence N")` |
| 6 | 终态事件不超过 1 个 | `LedgerCorruptionError("multiple terminal events")` |

`ENOENT` 与空文件都返回 `[]`（新 Run 的正常情况）。

第 1 条是**部分写入检测**：进程在 `writeFile` 中途被杀会留下半行，此时整个账本被判定为损坏而不是"少了一条事件"。这是把不确定性显式化的做法。

### 3.7 hash 覆盖范围

`event_hash` 覆盖除自身以外的**全部字段**，包括 `sequence`、`occurred_at`、`attempt`、`idempotency_key`、`data`、`previous_event_hash`。因此：

- 改动任何字段（含顺序）→ 第 3 道校验失败
- 删除中间任意一条 → 第 4、5 道校验失败
- 插入伪事件 → 后续链断裂

### 3.8 两个错误类型

`EventInvariantError`（写入期契约违反）与 `LedgerCorruptionError`（读取期数据损坏）是不同类别，调用方据此区分"我用法不对"与"磁盘上的东西坏了"。

### 3.9 G-04 Action WAL 与 Recovery Ledger

`ActionWal` 和 canonical Event Ledger 是两个职责不同的 hash-chained 事实源：前者先证明“准备修改什么、磁盘是否已跨过 mutation 边界”，后者再证明用户可见的 Receipt/Event。每个 Action WAL record 复制不可变 transaction identity，并按 `prepare → applied → committed → verified` 推进；未改盘的 prepare 可转 `aborted`。`committed` 绑定 patch event/receipt id，`verified` 绑定 verification event id。

既存目标的 exact before-image 使用独立 data + metadata 文件，metadata 绑定 project/run/action/path/hash/length；读取 rollback bytes 时再次验证 scope、owner/权限、regular file、长度与 hash。backup 不是公开 Artifact，也不做会改变字节的脱敏，因此只依赖本地私有权限，**不是加密备份**。

WAL 与 `RecoveryLedger` 的每次逻辑追加同样走完整候选文件的临时写入/fsync/rename/目录 fsync，并验证 sequence、previous hash、immutable identity 与 phase transition。Recovery Ledger 将 `replay_missing_event / restore_from_backup / mark_diverged` 的 started/terminal 行物化为 attempt，自动尝试默认最多一次并支持 Markdown 导出。rollback 会在 restore syscall 前先留下 open attempt；若崩溃发生在 bytes 已恢复但 Event 未写之间，启动以 before hash 补齐唯一 `patch.rolled_back` / `action.reconciled`，不会重复 restore。当前没有 Host/Web 报告导出接口。

### 3.10 G-15 Telemetry 的提交后派生边界

Telemetry 不是 `JsonlEventLedger` 的第二个 subscriber/存储格式。Runtime 的 `#appendScopedInOrder()` 先等待 `ledger.append()` 完成，随后把返回的**已提交 `SessionEvent`**交给 `RuntimeTelemetryProjector.record()`，再继续 Session ref 索引与 Live publish。投影器只选定 bounded 字段，并自行吞掉未来/legacy payload 的解析异常；`SafeTelemetry` 再隔离 sink 的 `emit`/`flush` 异常。已经 durable 的 Event 不可能因为 OTLP/自定义 sink 故障而变成 append 失败。

这个顺序不是“两份同等账本的双写”：Telemetry 可以丢失或重复，Ledger 始终权威。恢复、Projection、WAL 对账、Session repair 都只读 Ledger/Artifact/WAL，不读 sink；启动不会回放历史 Ledger 去补发 Telemetry。terminal Event 只触发非阻塞 safe flush，CLI 关停在 Host close 后可再 await best-effort flush，但该 Telemetry barrier 只有默认 5 秒总等待预算。

## 4. `ArtifactStore`

### 4.1 常量

| 常量 | 值 |
|---|---|
| `DEFAULT_MAX_WIRE_BYTES` | `1024 * 1024`（1 MiB） |
| `DEFAULT_MAX_INTERNAL_BYTES` | `8 * 1024 * 1024`（8 MiB，Runtime 恢复与 G-02 受控回读） |
| `ALLOWED_WIRE_MIME_TYPES` | `application/json`、`text/markdown`、`text/plain`、`text/x-diff` |

`initialize()` 会以 `0700` 创建/收紧 Artifact root，拒绝 symlink、非目录与 POSIX 上非当前用户 owner；`put()` 以 `0600`、`wx` 创建 data 与 metadata。公开 Host 路径只调用 `get()`，维持 1 MiB 上限；`getInternal()` 只供 Runtime 信任边界使用，当前服务于 Session 恢复与 G-02 archive/spill 源解析。它虽放宽到独立的 8 MiB 单工件硬上限，仍复用下述全部校验，也没有 Host 通用大文件路由。`read_artifact` 只是在这一内部边界内按当前 Run、最多 4,000 UTF-8 bytes/page 取回 Context archive；它不把 `getInternal()` 暴露给 Host/Web。这些权限控制不等同于静态加密。

### 4.2 `put()` 的写入次序

1. `sanitizeArtifactContent(content, mimeType)` ——**先脱敏再计算哈希**
2. `content_hash = sha256(bytes)`、`byte_length`
3. 写 `<id>.data`（`flag: "wx"`，已存在则失败）
4. 写 `<id>.json` 元数据（`flag: "wx"`）

注意第 1 步：**哈希是对脱敏后的字节计算的**，而且 JSON 会被 `JSON.stringify(..., null, 2)` 重新格式化。也就是说落盘内容与调用方传入的原始字符串并不相同——调用方不能假设"我传了什么，磁盘上就是什么"。

### 4.3 `get()` / `getInternal()` 的六道门

| 顺序 | 检查 | 失败状态 |
|---|---|---|
| 1 | 读取元数据（`ENOENT` → 后续 catch） | `unavailable: not_found` |
| 2 | `ref.project_id` / `ref.run_id` 与请求一致 | `unavailable: out_of_scope` |
| 3 | MIME 在白名单内 | `unavailable: unsupported_mime` |
| 4 | `byte_length <= 当前读取路径上限`（公开 1 MiB / 内部 8 MiB） | `unavailable: too_large` |
| 5 | 重新计算 hash 与 `content_hash` 一致 | `corrupt`（带 `expected_hash` 与 `actual_hash`） |
| 6 | 再次脱敏后**与原内容逐字节相同** | `corrupt: "artifact failed secondary redaction verification"` |

第 2 道门是**跨 Run 隔离**：即使知道 artifact_id，不同 project/run 也拿不到内容。

两条底层读取路径只在上限不同：`getInternal()` 不是绕过验证的后门，也没有 Host/SDK 通用路由。恢复载荷还会在 Runtime 中继续通过 `RunRecoveryStateSchema` / `SessionPendingPatchRecoveryStateSchema` 与 action binding 校验；G-02 则只允许 Context archive kind，并继续绑定当前 Run 与 content hash。模型侧 `read_artifact` 的 locator 不携带可选 project/run，Runtime 从正在执行的 Run 注入 scope；即使 Plain Chat 没有 Workspace read 能力，也只能分页读取自己该 Run 的 archive。

第 6 道门是最有含量的一道。脱敏函数是幂等的，所以正常路径下二次脱敏结果必然等于原内容；一旦不等，说明磁盘上的内容含有**写入时未经过脱敏**的东西（被篡改，或由旧版本/外部工具写入）。此时返回 `corrupt` 而不是"照常返回"，把泄漏风险转成显式的证据不可用。

### 4.4 JSON 工件为什么单独处理

```194:205:packages/core/src/artifact-store.ts
function sanitizeArtifactContent(content: string, mimeType: string): string {
  if (mimeType !== "application/json") return redactSensitiveText(content);
  let parsed: unknown;
  try {
    parsed = JSON.parse(content) as unknown;
  } catch {
    // Do not include a parser excerpt because it may itself contain the secret
    // that caused an invalid producer payload.
    throw new TypeError("application/json Artifact content is invalid JSON");
  }
  return JSON.stringify(redactStructuredArtifactValue(parsed), null, 2);
}
```

catch 块里的注释值得注意：**解析失败时不附带解析器摘录**，因为摘录本身可能含有机密。

### 4.5 G-05 当前 Run Artifact 索引

`list_artifacts` 不扫描磁盘目录，也不信任模型提供 scope；Runtime 从当前 Run 的 canonical Event Ledger 汇总 `artifact_refs`，核对 project/run、按 artifact id 去重、排除内部 `recovery_state`，再返回稳定分页的公开 metadata。正文从不进入 listing。

这份 listing 也不会被保存为新 `tool_output` Artifact，否则它会在下一页/下一次调用中列出自己并永久增长。它仍留下正常 Tool Receipt/Observation 与 Event；只是 metadata JSON 不复制成新的大载荷。发现 locator 不等于读取授权，`read_artifact` 继续只读当前 Run 的 G-02 Context archive。

## 5. `projectRun()`

### 5.1 状态推导表

投影只识别下列事件推进 `status`；Todo 与 G-14 steering 事件虽然不改变 status，还会分别推进 `todos` 与 `input_queue`，其它事件仅进入 `timeline`：

| 事件 | status 变化 | 副作用 |
|---|---|---|
| （初始） | `created` | — |
| `run.started` | `data.phase === "indexing"` ? `indexing` : `running` | — |
| `context.built` | `running` | — |
| `plan.ready` | `awaiting_plan_approval` | 设置 `{plan_event_id, todo_ids}` 为 `pending_plan` |
| `plan.approved` | `running` | 清空 `pending_plan`，mode 切为 `execute` |
| `approval.requested` | `awaiting_approval` | 解析并脱敏 `pending_approval` |
| `approval.granted` / `denied` / `expired` | `running` | 清空 `pending_approval` |
| `action.diverged` | `needs_manual_review` | 清空 pending approval；`failure_code = "action_diverged"` |
| `run.interrupted` | `interrupted` | 清空 `pending_approval`；保留既有证据供恢复判断 |
| `run.resumed` | `restored_status === "interrupted"` → `interrupted`；`"awaiting_plan_approval"` → `awaiting_plan_approval`；其余 → `running` | Plan 恢复保留 Ledger 重放出的 `pending_plan`；Patch 待审批恢复随后由新的 `approval.requested` 推进 |
| `run.completed` | `completed` | `outcome = redact(data.outcome ?? summary)` |
| `run.failed` | `failed` | `outcome = redact(summary)`，`failure_code = data.code ?? "run_failed"` |
| `run.cancelled` | `cancelled` | `outcome = redact(summary)` |

`artifact_refs` 由全部事件的 `artifact_refs` 按 `artifact_id` 去重汇总。`todos` 则通过同一组 Event 的 `todo.created|updated|completed|blocked` 投影；其中 `last_sequence` 是本次重放所见的完整 Run Ledger 尾序号（`events.at(-1)?.sequence`），不等同于“最后一条 Todo Event”。依赖存在、无环、状态专用 Event 与最多 500 条继续由 Todo schema 二次校验。

Todo replay 还对模型完成证据使用与 live write 相同的 fail-closed predicate：只接受同 Run 中更早出现的成功非 Todo `tool.completed`、带严格成功 `run_test` Receipt 的 `test.completed`，以及 `action.verified/reconciled`、`patch.preview_created/applied`、`graph.snapshot_created/delta_created`。Todo/Plan/Model/Policy/Approval/lifecycle Event 会被记录为 ineligible，不能靠“账本里确实有这个 id”自证；已有证据的 done Todo 在保持 done 时也不能清空证据。这条关联证明的是 durable execution fact，不会判断该事实是否在语义上满足某条 Todo 的验收标准。用户 `todo.completed` 是对自身的 actor-bound 确认，不进入另一条 Todo 的模型证据 allowlist。

`input_queue` 完全由 `user.input_queued/consumed` 重建。纯旧 Ledger 没有这两类 Event 时默认 `{pending:[]}`；新 Event 则必须通过独立 strict payload schema。重放允许相同 canonical input 的重复 queued fact 幂等合并，但以下情况全部抛 `ProjectionError`：同 `input_id` 的正文或 `_internal_input_digest` 冲突、Event/input/Run scope 不一致、pending 超过 100、消费未知或已消费 input、kind/`queued_event_id` 不匹配、消费时间早于提交时间、`at_step` 不严格递增。`pending` 保持账本入队顺序并对 body 再脱敏，`last_consumed` 只公开最小消费事实；终态不会伪造“已消费”来清空尚未处理的 durable input。

Runtime 在 queued payload 顶层写 `_internal_command_digest` 与 `_internal_input_digest`：前者检测同 `command_id` 不同 raw payload，后者覆盖不同 command 重用同 `input_id` 且正文脱敏后碰撞的情况。两者参与 canonical Event hash 与恢复检查，但不是公开凭据或授权；`toWireEvent()` 在结构化脱敏前删除所有顶层 `_internal_*`，因此不会进入 timeline 或 Web。

`subagents` 完全由五种 `subagent.*` Event 派生。旧 Ledger 默认 `{items:[],active_count:0,last_sequence:0,limits:{max_parallel_subagents:2,max_depth:1}}`。每个 child 的 link、冻结 profile authority、context scope、budget/depth、消息数、终态与有界 result 都从父 Ledger 重建；完整 child 账本不嵌入这个投影。projector 拒绝未知/重复 child id/run/session、链接跨 scope、非 initial 首消息、终态后消息、超并发/深度/不一致 limits，以及 parent 在 active child 尚未归零时终态。只有 `failure_stage:"launch"` 允许在 initial message 落账前以 started→failed 收口；execution/completed/interrupted 仍必须有 initial task。

七条必须记住的语义：

1. **首事件必须是 `run.created`**，否则 `ProjectionError("run.created must be the first event")`。
2. **`approval.expired` 把状态退回 `running`**——审批过期不终止 Run，只是撤销待批状态。
3. **`tool.started/batch_started/batch_completed/completed/failed`、`action.rejected`、`policy.denied`、`model.*` 都不改变 status**。Run 层的状态机是粗粒度的，细节只在 `timeline` 里。因此**不能用 `status` 判断"此刻是否在执行工具"**。
4. **`action.diverged` 的人工复核状态保持粘性。** 最终汇总会把 status 固定为 `needs_manual_review`，后续普通终态或维护 Event 不能把真实文件分歧遮成 completed/failed。
5. **Plan approval 绑定 Event revision。** Todo 改动后 Runtime 会追加新的 `plan.ready`；投影只暴露最新 `pending_plan`，旧 `plan_event_id` 不能继续执行。
6. **Steering 重放 fail-closed。** 新 `user.input_*` Event 不是“尽量展示”的日志；任何 scope、幂等身份、消费引用或 step 顺序矛盾都会拒绝整个投影，防止重启后悄悄丢消息或重复消费。
7. **Subagent 重放 fail-closed。** parent terminal 必须晚于所有 active child receipt；terminal receipt 必须引用 child terminal event id/hash，不能用一段 summary 伪装 child 已收口。

### 5.2 投影期脱敏

投影阶段单独做了一次脱敏，覆盖以下路径：

- `run.created.data.task` → `redactSensitiveText`
- `approval.requested` 的 `preview.diff` → `redactSensitiveText`
- `run.completed/failed/cancelled` 的 `outcome` → `redactSensitiveText`
- `input_queue.pending[].body` → `redactSensitiveText`
- 每个事件的 `summary` 与 `data`（经 `toWireEvent`）
- 所有 `data` 中以 `_internal_` 开头的恢复引用或幂等 digest 在 wire 投影前剥离

### 5.3 `toWireEvent()` 的剥离

```
保留：schema_version, event_id, project_id, run_id, session_id?, sequence, occurred_at, type,
      summary(脱敏), artifact_refs, 以及全部可选关联 ID
剥掉：attempt, idempotency_key, previous_event_hash, event_hash
重写：data = redactStructuredValue(移除 `_internal_*` 后的 event.data)
```

**wire 平面拿不到 hash 与幂等键**，因此浏览器无法伪造或校验证据链——它只能消费投影。

### 5.4 G-13 Sandbox report 的可重放选择

`projectRun()` 按事件 sequence 扫描 `sandbox.enforced` / `sandbox.disabled` 以及带执行期报告的 `tool.completed|failed|unknown`，只接受 `SandboxReportSchema` 校验成功的顶层 `event.data.sandbox_report`；无关 Event 中同名/相似字段不会覆盖。最后一份合法报告成为 `RunProjection.sandbox_report`，因此重放得到和在线查询相同的 run-level enforcement。

该字段为 G-13 之前的 Ledger 保持 optional。`sandbox.configured` 只证明 Host 选择了 mode/platform，不能冒充 enforcement；真正的 `full/partial/none` 必须来自 enforced/disabled 或工具实际执行报告。`run_test` 同时把报告放进 Receipt metadata 与 Observation facts 供逐事件检查，但 Projection 只信顶层、schema-validated copy。

## 6. `crypto.ts`：脱敏的三个层级与精确值守卫

| 函数 | 用途 | 字符串上限 | 集合上限 | 深度上限 |
|---|---|---|---|---|
| `redactSensitiveText` | 纯文本 | 无 | — | — |
| `redactStructuredValue` | 事件 `data` 出站 | 8 000 | 100 项 | 8 |
| `redactStructuredArtifactValue` | JSON 工件 | **无** | **无** | 100 |

前两个是"投影导向"的，会截断；第三个刻意**不截断**，注释解释了原因：

> *Artifact hashes describe the complete stored payload, so silently dropping array members, object properties, or string suffixes here would make an apparently valid evidence object incomplete.*

即：工件哈希描述的是完整载荷，静默丢成员会让一份"看起来有效"的证据实际上不完整。剩下的唯一限制是深度守卫（100 层），防止对抗性 JSON 打爆调用栈。

`registerSecretForRedaction(value)` 会在凭据进入 Host 时登记其**精确值**；登记值保留到进程结束，避免轮换后的旧 Key 在后续 Ledger/Artifact 写入中重新泄漏。精确守卫同时登记 raw 与 JSON-string encoded 形态，因而含引号/反斜杠的值被供应商错误 JSON 回显时也能命中。结构化脱敏会同时处理 value 与动态 object key；key 脱敏发生碰撞时用 `#2`、`#3` 保留后续槽位而不恢复原 key。`redactSensitiveText` 先做最长优先的精确替换，再做以下形态匹配：

1. 已登记的精确凭据值 → `[REDACTED_REGISTERED_SECRET]`
2. PEM 私钥块（`-----BEGIN ... PRIVATE KEY-----`）
3. `sk-` 前缀 API key（≥12 字符）
4. `gh[pousr]_` GitHub token
5. `xox[baprs]-` Slack token
6. `AKIA` + 16 位 AWS access key
7. 引号包裹的键值赋值（JSON 风格）
8. 裸键值赋值（`key=value` / `key: value`）
9. `Bearer <token>`
10. 本机路径 → `[REDACTED_LOCAL_PATH]`（`/Users`、`/home`、`/tmp`、`/private`、`/var`、`/Volumes`、`/opt`、`/etc` 前缀，通用绝对路径，Windows 盘符路径）

敏感键判定 `isSensitiveKey()` 采用"归一化后精确匹配 + 后缀匹配"：

```
精确：apikey authorization credential cwd password privatekey realroot refreshtoken secret token
后缀：token secret password apikey accesskey privatekey credential
```

注意 `cwd` 与 `realroot` 也在列表中——**工作区真实根目录永不外泄**。

还有一个反向工具 `containsSensitiveStructuredData(value, depth=12)`，供需要"只判断不修改"的场景使用。

### 6.1 G-19 的最终持久化边界

- `JsonlEventLedger.append()` 在 hash 计算与 JSONL 写入前再次对 `summary` 和 `data` 脱敏，因此启动迁移等不经过 `AgentRuntime` 的维护事件也受同一守卫保护。
- `ArtifactStore.put()` 在计算 Artifact hash 和写盘前脱敏；读取时再做一次脱敏并要求字节完全一致，否则返回 `corrupt`。
- `recordCredentialMigration()` 用稳定 migration id 把迁移幂等写成 `system:tracegraph` 的三事件维护 Run：`run.created → credentials.migrated → run.completed`。非敏感 outbox 在终态提交前保留，重启可从任一中断点补齐；事件只含凭据名、backend、迁移时间和来源，不含 secret reference，更不含 secret value。

### 6.2 G-03 的 durable usage 事实

- `context.built` / Context Manifest 保存请求前 `token_estimate`：estimator、confidence、input/output 与六类 `per_section`。它是 applied preflight，不会在 provider 返回后被改写。
- `model.usage_reported` 保存 provider/model、input/output/total、可选 cache/reasoning、请求 kind/sequence、preflight 对照与成本状态；初始请求校准成功时还含 `delta_ratio` / calibration revision。
- `model.usage_anomaly` 只在初始请求 input 与 preflight 的绝对偏差超过 25% 时追加，并复用相同 `model_call_id`、request kind/sequence。repair report 单独落账但不校准。
- 成本不是本地推导：只有 provider 明确回报 amount + currency 才持久化；否则 `cost_status: "unavailable"`。

Web 历史视图直接从 `RunProjection.timeline` 按 `model_call_id` 配对这些 durable Event 与 Context，而不是依赖进程内 `ModelSurfaceEvent`。但 provider response 和 usage append 没有跨系统事务：若进程在两者之间崩溃，账本会缺这次 usage；当前 G-04 只保护 Patch Action，并不负责 provider 用量补账。

### 6.3 G-15 的 allowlisted 派生，而不是复制 Event

`RuntimeTelemetryProjector` 只把 run/model/tool/batch/compaction/approval/sandbox 的 selected scalar fields 变成 bounded span/metric/log。它不复制 `summary` 或任意 Event `data`，也不发送 Prompt、最终回答、真实路径、secret、原始 Tool output。`model.tokens.total` / 明确 provider-reported `model.cost` 来自 G-03 durable usage；`tool.call.output_bytes` 来自 canonical Receipt metadata，是 bounded/validated `RawToolResult` envelope 的精确 UTF-8 字节数，`tool.call.artifact_bytes` 则只统计该 Event `artifact_refs[].byte_length` 的已持久化总和。两者是不同口径，都不复制原始结果。

公开的 `tracegraph.telemetry-status.v1` 只报告 sink、disabled/active/degraded、错误计数与可选最后错误时间。endpoint、header、credential、配置 path 与 queued payload 均留在 Host；status 不进入 Event Ledger，也不参与恢复。

## 7. 不变量清单

1. 一个 Run 一个 jsonl 文件；`sequence` 从 1 开始严格 +1。
2. `event_hash` 覆盖除自身外全部字段；`previous_event_hash` 必须与上一条的 `event_hash` 相等。
3. 一个 Run 至多一个终态事件；终态后只允许明确白名单中的 late/session/G-04 maintenance 事实，不能重启执行。
4. 文件尾部必须完整（以 `\n` 结尾），否则整体判损坏。
5. 带 `idempotency_key` 的重复 append 返回原事件且不写入。
6. 工件哈希基于**脱敏后**的字节；读取时二次脱敏必须逐字节相同。
7. 工件读取受 project/run 双维度隔离。
8. 订阅者异常不影响已落盘事件的成功语义。
9. wire 平面不携带 `event_hash` / `previous_event_hash` / `idempotency_key` / `attempt`。
10. 已登记凭据值（含 JSON 编码形态和动态 key）在 Ledger 与 Artifact 的最终写边界再次脱敏；迁移事件只能记录安全元数据。
11. Session JSONL 只含 strict header/event-ref；恢复状态在内部 Artifact 中，`_internal_*` 引用不会出现在 wire。
12. Ledger→Session ref 是顺序双写而非跨文件事务；崩溃窗口以 Ledger 为权威。G-04 仅补齐恢复中相关 Action Event 的 ref，不做通用全量反向扫描。
13. Context Manifest 的逐 section 值只代表不可变 preflight；provider report 只追加后续 Event，不反写或伪造逐 section 精确账。
14. repair usage 与 initial usage 按 kind/sequence 分开；repair 不参与初始 Context 的 calibration。
15. `verified` Action WAL 必须绑定 durable patch/verification 事件；`prepare + before` 只能关闭为 aborted，未知 hash 只能进入 divergence，不能自动恢复字节。
16. before-image 只从经过 metadata/scope/hash/权限复核的私有 backup 读取；显式 rollback 也必须先匹配当前 after hash。
17. batch lifecycle 只追加结构化调度事实：started/completed 用独立 strict schema 在 Runtime append 前校验；工具原文仍只走受限 Observation/Artifact，不复制进 batch Event。
18. `list_artifacts` 只从当前 Run 已引用的公开 Artifact 构造 metadata；排除 recovery state、不返回 content，也不把 listing 再存成 Artifact。
19. `sandbox_report` 只能由合法 lifecycle/Tool Event 推进；`sandbox.configured` 与无关 Event 不能伪造 enforcement，旧 Ledger 无报告仍须可重放。
20. `pending_plan` 永远取最新 `plan.ready`，`plan.approved` 必须引用该 Event；Todo 投影只消费 strict mutation Event，不从 UI 或 Tool summary 猜状态。
21. Todo 写命令在状态校验前先做既有 `command_id` 幂等/冲突判断；同 key 同 payload 返回原结果，同 key 异 payload 拒绝，不能因 Run 后来终态而改变已提交命令的答案。
22. G-14 inbox 最多保留 100 条 pending input；同 `input_id` 最多消费一次，消费必须绑定原 queued Event 且 `at_step` 严格递增。command/input digest 只参与 canonical 幂等与冲突检查，不得出 Wire。
23. G-15 Telemetry 只能从 Ledger append 成功返回的 Event 派生；sink failure 不能影响 canonical commit。Telemetry/status 不能作为恢复、投影、Action 对账或审计替代，默认 noop 不产生外部 I/O。
24. G-07 父侧 `subagents` 只能由五种 strict lifecycle Event 重建；child id/run/session/link/limits 必须稳定，首条正常消息必须是 `initial_task`，terminal 后不得追加消息，parent 终态前 `active_count` 必须归零。仅 launch failure 可无 initial message。

## 9. 已知缺口与未完成分支

1. **durable replace 仍不是跨文件事务或跨进程锁。** Event Ledger、Action WAL、Recovery Ledger 各自使用 file/directory fsync 的原子替换，但三者与真实 workspace 文件之间仍靠 phase/hash 对账收敛，不是一次原子 commit。各自的 Promise queue 只覆盖单进程；没有跨 Host 的 workspace target lock。

2. **Event Ledger 自身的 `#queue` 仍只保证单进程。** G-01 Runtime 的正常 Session 路径在 append 前持有跨进程 lease，第二 Host 会被 409 拒绝并留下脱敏结构化 Host audit；但直接绕过 Runtime/Session Store 使用 `JsonlEventLedger` 仍没有文件锁。维护类 Run 等不属于同一 Session 的并发写入也尚无通用跨进程 WAL。

3. **每次 append 都全量读取该 Run 的历史。** `#readList()` 需要读完整文件来算 `previous_event_hash`、`sequence` 与终态检查，因此单次 append 是 O(n) I/O，长 Run 的写入成本随事件数线性增长。没有快照或尾部缓存。

4. **`stableStringify` 用 `localeCompare` 排序对象键。** 哈希的可复现性因此隐含依赖运行环境的排序稳定性。对 ASCII 键（当前全部场景）一致，但这是一个隐藏的环境耦合点；若将来出现非 ASCII 键，跨环境复现 hash 需要重新评估。此外该函数把非数组、非对象的 `undefined` 交给 `JSON.stringify`，得到 `undefined` 字符串而不是抛错。

5. **`redactStructuredValue` 会截断出站数据**（字符串 8 000、集合 100 项、深度 8），而 canonical 账本里是完整的。因此**投影视图与账本内容存在系统性差异**，任何"UI 显示的就是事实"的推断都是错的。这是有意的，但需要在文档与 UI 文案上保持诚实。

6. **工件 `get()` 没有 range 支持。** 契约里的 `ArtifactAvailableSchema` 预留了 `range: {start, end, total}` 可选字段，但 `ArtifactStore.get()` 从不上报它——要么整份返回，要么因超限返回 `too_large`。大文件的部分读取能力只存在于契约中。

7. **投影不校验 `pending_approval` 的失败原因。** `approval.requested` 里若 `pending_approval` 解析失败，代码静默跳过（`safeParse` 失败即不设置 `pending_approval`），但 `status` 仍然被置为 `awaiting_approval`。这会造成"状态说等待审批、但没有可审批内容"的视图不一致。

8. **`workspace_kind` 的三元兜底是 `disposable_fixture`。** 若 `run.created.data.workspace_kind` 缺失或为未知值，投影会默认为最宽松的 fixture 类型，而不是报错。能力展示因此可能高估实际权限。

9. **`attempt` 字段缺少消费方。** 它进入 hash 并落盘，但投影与出站都不使用它，也没有"第几次尝试"的可视化。重试语义目前只体现在账本里。

10. **provider usage 没有 response→Ledger WAL。** Runtime 会在 decision 或 request failure 之前尽快 append，但进程仍可能在 provider 已返回后退出，导致已计费调用没有 `model.usage_reported`；校准当前先原子落盘再 append Event，所以极窄窗口内派生 calibration revision 也可能领先 Ledger。当前没有从 Ledger 重建校准或从 provider 自动反查；Patch 专用 G-04 不覆盖该窗口。

11. **新增事件沿用 schema v1。** 这保持了既有 Event 信封语义，但外部消费者若把 `tracegraph.session-event.v1` 的枚举硬编码为旧集合，会拒绝 G-03/G-04/G-05/G-13/G-09/G-14/G-21/G-07/G-18/G-17/G-08/G-12/G-20 新事件。G-21 当时把集合增至 68 且 projector 仍为 v5；G-07 后为 73 种/projector v6；G-18 后为 76 种/projector v7；G-17 后为 77 种/projector v7；G-08 后为 90 种；G-10/G-11/G-12 后为 100 种；G-20 再追加 `code.intel_updated` / `code.stale_base_detected` 后当前必须接受 102 种事件，以及 projector v9 的可选 `team`、`code_intel`、`needs_manual_review`、`awaiting_plan_approval`、Todo、`input_queue`、`subagents`、`attachments`、`diagnostics_summary` 与可选 `sandbox_report`。

12. **G-05 ordered append 仍只在进程内。** Runtime 的 per-run Event/Session append queue 防止同一 batch 的并行工具分叉 parent chain；Artifact 则逐工件原子 durable 写入。两者都没有跨 Host 协调或跨进程锁。

13. **G-15 Telemetry 没有 durable delivery。** OTLP queue、`error_count`、`last_error_at` 和关联状态只在当前进程内，重启丢失；只有网络/超时失败及 HTTP `429/502/503/504` 重新入队，后续 flush 可能重复；`400` 等非可重试响应与 HTTP 200 `partialSuccess` 拒收计错后丢弃。200 正文只有界读取 rejected count，Collector 文本不回显。当前无自动 retry/backoff、持久队列、完整 OTel SDK/processor/sampling/propagation 或真实 Collector 集成验证，CLI 关停 flush 的 5 秒预算也不保证 drain，不能把 sink 当作 exactly-once 事实系统。

14. **G-07 父子收口仍有明确 fail-stop 窗口。** child terminal 已 durable、但父 terminal receipt 持续 append 失败时，父投影保留 active child，父 Run 保持 `running` 且 permit 不释放；必须重启 Host 后按 child Ledger terminal id/hash 对账。Runtime 不会在同进程猜测 terminal、释放 permit 或重启旧 child 模型循环。

15. **G-08 的原子性是单份 root Run Ledger 的原子批次，不是分布式事务。** `team.member_lost.reopened_task_ids` 在一个 Event 内同时标记失联与释放任务；`appendAtomic()` 又把 create+backfill、started+join 与 sweep 的全部 loss+receipt 各自以一次 root JSONL durable replace 提交。旧实现已留下的 partial sweep tail 仍可用原 command id 补齐；新写路径不再制造该窗口。这仍没有跨 root/child Ledger、Session、Workspace、外部系统或跨 Host 的事务/consensus；失联任务只回到 open，不会自动重派。
