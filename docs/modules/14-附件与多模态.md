# 模块 14：附件与多模态（G-18 / MEDIA-094）

> 定位：用户上传的 PNG、JPEG、PDF 是受 scope、hash 与 Ledger 约束的 Run 输入；MEDIA-094 增加经过校验的 PNG 生成和结构化 SVG 绘图输出，两者都以 scoped Artifact 和 canonical receipt 证明。
> 代码：`packages/contracts/src/attachment.ts`、`packages/core/src/domains/evidence/attachment.ts`、`packages/core/src/domains/runtime/runtime.ts`、`packages/core/src/domains/model/model-provider.ts`、`packages/host/src/webserver/index.ts`、`packages/sdk/src/index.ts`、`packages/workbench/src/`
> 实现状态：**已实现/已验证**；G-18 完成时 canonical Event 为 76 种、projector v7，经 G-17、G-08、G-10、G-11、G-12、G-20 与 MEM-042 追加后当前为 103 种；`PROJECTOR_VERSION = tracegraph.projector.v9`

## 1. 附件输入边界

当前支持：

- 媒体类型：`image/png`、`image/jpeg`、`application/pdf`；声明 MIME 还必须与 magic bytes 一致。
- 产品额度：单文件最多 5 MiB，每个 Run 最多 8 个附件，空文件拒绝。
- 创建新任务时上传：Plain Chat、项目 Ready 状态和终端 Run 的后续任务均可使用。
- 图片默认 `offload`；用户显式勾选“Send image to model”才请求 `inline`，并仍受 Host-owned 模型能力约束。
- PDF 永远引用原文件；抽取到的文本存为独立 `context_source_archive` Artifact。

当前不支持：运行中 steering 追加附件、在 Replay 中读取二进制、OCR、把 PDF 当图片发给模型、从 provider/model 名称自动猜测图片能力。

## 2. 两阶段 `stage → claim`

附件不是先创建 Run 再把原始字节塞进命令 JSON，而是分两阶段：

1. Web/SDK 用 `POST /api/attachments` 发送 raw `application/octet-stream`。query 只含 `command_id`、目标、声明 MIME、delivery 与可选 Session；Host 将浏览器目标解析成自己的项目 capability，并强制来源为 `user_upload`。
2. Core 在私有 staging 目录写入 scope、签名、hash、到期时间与 receipt；公开 receipt 只返回 opaque `upload_id`，不泄露 Plain Chat 的隐藏 project id。
3. StartRun/StartChat 只携带 `attachment_upload_ids`。Runtime 在 `run.created` 之后、`permission.configured` / sandbox / `run.started` / 首次模型请求之前认领每个 upload。
4. 认领重新校验 project/session、TTL、owner、字节 hash、MIME magic 与模型能力，然后写 `attachment.added` / `attachment.rejected` / `attachment.offloaded`。

默认 staging TTL 为 15 分钟。upload id 由 command 与 scope 稳定派生，因此丢失响应后的同请求重试可重放同一 receipt；同一 upload 被其它 Run 认领会 fail-closed。同一 Run 的 claim 结果也持久化，崩溃重试不会重复制造事实。

Host 的 raw transport hard cap 是 6 MiB，故业务上 `5 MiB + 1 byte` 可以先完整进入 staging 校验，再在 Run 中形成 `too_large` 的 durable rejection；6 MiB 不是可用额度。

## 3. Artifact、去重与 PDF 降级

通过校验的原文件按 project/run/media/hash/source 去重并进入 Artifact Store：

- 原始图片/PDF 的 `artifact_id` 同时是 `attachment_id`；Event data 只保存 `AttachmentRef` 与 locator，不保存 base64 或原始字节。
- `attachment.added.artifact_refs` 必须证明原文件；PDF 抽取成功时还必须证明独立文本 Artifact，二者的 project/run/hash/bytes/kind 必须与 payload 一致。
- 图片 offload 和所有 PDF 会再写 `attachment.offloaded`，locator 必须精确等于 `artifact:<attachment_id>`。
- 默认 PDF 提取器只做保守 literal-text 提取，不做 OCR。加密、压缩或没有可抽取文本时，`pdf_extraction` 明确记录失败原因与 `fallback: "reference_only"`；原 PDF 仍可按引用下载，不会假装模型已经阅读正文。

二进制文件不进入 Run JSON、Context Manifest、日志或 Event data。在线内容读取还会再次核对 Run Projection 的附件关系、MIME、长度与 SHA-256，并返回 `private, no-store`、`nosniff`、same-origin 与 sandbox CSP 响应头。

## 4. 模型内联规则

`ModelAdapter.capabilities()` 的 `image_input` 是 Host-owned、显式、默认 false 的能力。已保存服务通过 `image_input_models` 声明其已配置模型中的图片输入能力；Web/Desktop 设置提供逐模型选项，CLI 的模型保存请求使用相同字段。未声明模型保持关闭，不从服务名或模型名猜测。声明不代表已验证：文本连接测试不验证图片支持，实际发送仍需用户明确勾选图片内联，并以 Provider 请求及规范接纳/拒绝事件证明结果。每轮受理时冻结对应适配器能力，后续修改只影响新任务。`TRACEGRAPH_MODEL_IMAGE_INPUT=true`（也接受 `1`）保留为旧默认/环境配置的兼容入口；`false` / `0` 关闭，其他值使启动失败，正常已保存服务不需要该环境变量。

只有以下条件全部满足，首个模型请求才包含图片 block：

1. 附件是真实 PNG/JPEG；
2. 用户为该图片显式选择 `delivery: "inline"`；
3. 当前模型适配器声明 `image_input: true`；
4. stage/claim 的 scope、hash、大小与 magic 校验全部通过。

OpenAI-compatible 使用 `image_url` data URL，Anthropic 使用 base64 image source。能力为 false 时，Core 写 `attachment.rejected {code:"model_image_unsupported"}`，并在调用 provider transport 之前停止该图片进入模型；默认 offload 图片只以 Observation/Artifact 引用参与文本 Context。repair 请求不会重复携带图片。

## 5. 可重放 Projection 与 Web

G-18 新增三种 canonical Event：

- `attachment.added`：接收成功、Artifact 证明、delivery、去重与 PDF 抽取结果；
- `attachment.rejected`：拒绝码、大小、声明/探测 MIME 与原因；
- `attachment.offloaded`：默认外置、PDF 引用或未来 Context 外置原因与 locator。

`RunProjection.attachments` 由 Ledger 重放，不依赖 staging 目录或 Web 状态。Projector 对重复/conflicting upload、scope 不一致、缺失 Artifact proof、PDF 文本引用错误及无对应 added 的 offloaded 事件 fail-closed；旧 Ledger 得到 `{items: [], last_sequence: 0}`。因此新增派生形状把 projector 从 v6 升到 v7，但 Event 信封仍为 `tracegraph.session-event.v1`。

Web `AttachmentComposer` 默认 offload，并在本地先做类型、空文件、5 MiB 与 8 个上限提示；服务端仍独立重验。Trajectory 的附件卡片展示 durable added/rejected/offloaded 与 PDF 抽取状态；在线模式按需加载图片 Blob URL 或提供 PDF 下载，并在替换/卸载时撤销 URL。Replay 只展示当时投影的 metadata/status，附件预览明确禁用，避免 replay bearer 越过所选历史前缀读取二进制。

## 7. MEDIA-094 图片生成与本地绘图输出

此能力与附件输入独立：`generate_image` 从明确配置的远端图片协议获得 PNG；`render_diagram` / `render_chart` 由受限结构化数据创建自包含 SVG。三者都是可信工具扩展，由 Runtime 的正常 policy、取消、Tool → Receipt → Observation → Ledger 链路执行。Plain Chat 也可发布本 Run 的媒体 Artifact，但不会因此获得项目文件读写、shell 或 patch 能力。外部执行许可仍由 Host policy 裁决，不能只根据文件系统只读标志推断图片请求许可。

成功必须先验证实际字节并写入本项目 / Run 的 Artifact Store，然后在 `tool.completed` 的 receipt 与 Event proof refs 中记下相同 Artifact ID、MIME、长度和 SHA-256。代码、解释性文本、Markdown 图片链接、远端 URL 或 HTTP 200 本身均不是图片成功。原有文本 Artifact 接口不返回二进制。

| 当前入口 | 实际范围 |
|---|---|
| `GET/POST/DELETE /api/image-provider` | 独立图片配置，显式选择 `openai-images` / `openai-responses` / `openai-chat-images`；只公开有无 key 的 metadata，私有配置存 credential reference |
| `POST /api/media/runs` | 闭合类型化 generate / diagram / chart operation；Host 内部一键适配器走正常 Runtime，不需要聊天模型；command 相同且全部参数相同复用原 Run，参数变化 409 |
| `GET /api/runs/:runId/artifacts/:artifactId/content` | live-only / 同项目同 Run 关系绑定；存储与 SDK 均重验 hash / MIME / bytes；Replay 拒绝二进制读取与生成 |
| SDK | `getImageConfig`、`configureImageProvider`、`clearImageProvider`、`startMediaRun`、`getArtifactContent` |
| CLI | `outlive image get/configure/clear`；`outlive media generate/diagram/chart/export`；key 只走 stdin，导出不覆盖已有文件 |
| Web / Desktop 共享 UI | 图片设置和媒体入口消费真实能力与上述 SDK；图库只能采用实际成功 receipt 的 Artifact，不从模型 prose 推断生成完成 |

图片生成当前只支持 PNG，最大 20 MiB；校验 PNG chunk CRC、IHDR 和实际 IDAT 解压行。当前解码子集为 8-bit、非隔行灰度 / RGB / alpha，边长最多 8192，像素总数最多 16,777,216。生成 JPEG/WebP 明确返回不支持，而不是仅核验 magic bytes 后宣称解码成功；原有附件 JPEG 输入继续按原边界处理。Responses 要求 completed 的 image generation call；兼容 Chat 只接受单个 PNG data URL，不宣称所有兼容服务商均支持该约定。

本地 SVG 不执行任意代码、HTML、Mermaid、导入 SVG 或外部资源；流程图最多 16 个唯一节点 / 32 条有效边，bar / line chart 最多 24 对标签与 ±1e9 有限数值。标签转义且拒绝 XML 无效字符，避免脚本注入与无效 SVG。一键本地绘图在 `run.created` 持久记录 Host 内部 admission `background_model_derivation:false`，后台 Memory 模型抽取包括恢复时都跳过该 Run。普通聊天和任务继续原抽取行为；Runtime 中适配器的 `model.request_started` 不是网络模型请求证据。

图片 provider 与 credential reference 在 Run admission 冻结；用户更改配置不会把进行中的 Run 换成新 endpoint / key，旧 key 租约到 terminal / cancel 才释放。派发后超时、网络异常与服务端不确定结果记录 unknown，不自动重试；取消不能保证远端没有消费或收费。显式 ask 策略仍要求可信一次性 approval answerer；普通非 Patch 的 UI 手动审批尚未接通时 fail closed，不制造已授权事实。

[源码与验收矩阵](../validation/media-094/README.md)记录最终真实 CLI / 分离 Host 的 **94 项断言、20 次 CLI、6 个实际文件**与[独立校验 666 项](../validation/media-094/evidence/source-final/independent-verification.json)。三种协议均使用确定性真实 HTTP 提供商，涵盖 scope / replay / corruption / malformed / auth / unknown / cancel / exact retry、未配置模型绘图与配置模型后零额外请求。DMG 真实安装后的[同链路验收](../validation/media-094/evidence/installed-mac-final/report.json)也通过 94 断言 / 20 CLI / 6 文件与[独立 666 检查](../validation/media-094/evidence/installed-mac-final/independent-verification.json)，只使用 app 自带 Node 与安装依赖。该证据证明协议、治理和字节输出；真实付费账户、提供商质量、计费和独立外部用户使用仍未知。
