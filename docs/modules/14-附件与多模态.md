# 模块 14：附件与多模态（G-18）

> 定位：把用户上传的 PNG、JPEG、PDF 变成受 scope、hash、Artifact 与 Event Ledger 约束的 Run 输入；默认只传引用，只有显式选择且模型声明能力时才把图片送进 provider。
> 代码：`packages/contracts/src/attachment.ts`、`packages/core/src/attachment.ts`、`packages/core/src/runtime.ts`、`packages/core/src/model-provider.ts`、`packages/host/src/index.ts`、`packages/sdk/src/index.ts`、`apps/web/src/`
> 实现状态：**已实现/已验证**；G-18 完成时 canonical Event 为 76 种、projector v7，经 G-17、G-08、G-10、G-11、G-12 与 G-20 追加后当前为 102 种；`PROJECTOR_VERSION = tracegraph.projector.v9`

---

## 1. 产品边界

当前支持：

- 媒体类型：`image/png`、`image/jpeg`、`application/pdf`；声明 MIME 还必须与 magic bytes 一致。
- 产品额度：单文件最多 5 MiB，每个 Run 最多 8 个附件，空文件拒绝。
- 创建新任务时上传：Plain Chat、项目 Ready 状态和终端 Run 的后续任务均可使用。
- 图片默认 `offload`；用户显式勾选“Send image to model”才请求 `inline`，并仍受 Host-owned 模型能力约束。
- PDF 永远引用原文件；抽取到的文本存为独立 `context_source_archive` Artifact。

当前不支持：运行中 steering 追加附件、在 Replay 中读取二进制、OCR、把 PDF 当图片发给模型、从 provider/model 名称自动猜测图片能力。

## 2. 两阶段 `stage → claim`

附件不是先创建 Run 再把原始字节塞进命令 JSON，而是分两阶段：

1. Web/SDK 用 `POST /api/attachments` 发送 raw `application/octet-stream`。query 只含 `command_id`、目标、声明 MIME、delivery 与可选 Session；Host 将浏览器目标解析成自己的项目 capability，并强制来源为 `user_upload`。
2. Core 在私有 staging 目录写入 scope、签名、hash、到期时间与 receipt；公开 receipt 只返回 opaque `upload_id`，不泄露 Plain Chat 的隐藏 project id。
3. StartRun/StartChat 只携带 `attachment_upload_ids`。Runtime 在 `run.created` 之后、`permission.configured` / sandbox / `run.started` / 首次模型请求之前认领每个 upload。
4. 认领重新校验 project/session、TTL、owner、字节 hash、MIME magic 与模型能力，然后写 `attachment.added` / `attachment.rejected` / `attachment.offloaded`。

默认 staging TTL 为 15 分钟。upload id 由 command 与 scope 稳定派生，因此丢失响应后的同请求重试可重放同一 receipt；同一 upload 被其它 Run 认领会 fail-closed。同一 Run 的 claim 结果也持久化，崩溃重试不会重复制造事实。

Host 的 raw transport hard cap 是 6 MiB，故业务上 `5 MiB + 1 byte` 可以先完整进入 staging 校验，再在 Run 中形成 `too_large` 的 durable rejection；6 MiB 不是可用额度。

## 3. Artifact、去重与 PDF 降级

通过校验的原文件按 project/run/media/hash/source 去重并进入 Artifact Store：

- 原始图片/PDF 的 `artifact_id` 同时是 `attachment_id`；Event data 只保存 `AttachmentRef` 与 locator，不保存 base64 或原始字节。
- `attachment.added.artifact_refs` 必须证明原文件；PDF 抽取成功时还必须证明独立文本 Artifact，二者的 project/run/hash/bytes/kind 必须与 payload 一致。
- 图片 offload 和所有 PDF 会再写 `attachment.offloaded`，locator 必须精确等于 `artifact:<attachment_id>`。
- 默认 PDF 提取器只做保守 literal-text 提取，不做 OCR。加密、压缩或没有可抽取文本时，`pdf_extraction` 明确记录失败原因与 `fallback: "reference_only"`；原 PDF 仍可按引用下载，不会假装模型已经阅读正文。

二进制文件不进入 Run JSON、Context Manifest、日志或 Event data。在线内容读取还会再次核对 Run Projection 的附件关系、MIME、长度与 SHA-256，并返回 `private, no-store`、`nosniff`、same-origin 与 sandbox CSP 响应头。

## 4. 模型内联规则

`ModelAdapter.capabilities()` 的 `image_input` 是 Host-owned、显式、默认 false 的能力。标准 CLI 只有设置 `TRACEGRAPH_MODEL_IMAGE_INPUT=true`（也接受 `1`）才启用；`false` / `0` 关闭，其他值使启动失败。

只有以下条件全部满足，首个模型请求才包含图片 block：

1. 附件是真实 PNG/JPEG；
2. 用户为该图片显式选择 `delivery: "inline"`；
3. 当前模型适配器声明 `image_input: true`；
4. stage/claim 的 scope、hash、大小与 magic 校验全部通过。

OpenAI-compatible 使用 `image_url` data URL，Anthropic 使用 base64 image source。能力为 false 时，Core 写 `attachment.rejected {code:"model_image_unsupported"}`，并在调用 provider transport 之前停止该图片进入模型；默认 offload 图片只以 Observation/Artifact 引用参与文本 Context。repair 请求不会重复携带图片。

## 5. 可重放 Projection 与 Web

G-18 新增三种 canonical Event：

- `attachment.added`：接收成功、Artifact 证明、delivery、去重与 PDF 抽取结果；
- `attachment.rejected`：拒绝码、大小、声明/探测 MIME 与原因；
- `attachment.offloaded`：默认外置、PDF 引用或未来 Context 外置原因与 locator。

`RunProjection.attachments` 由 Ledger 重放，不依赖 staging 目录或 Web 状态。Projector 对重复/conflicting upload、scope 不一致、缺失 Artifact proof、PDF 文本引用错误及无对应 added 的 offloaded 事件 fail-closed；旧 Ledger 得到 `{items: [], last_sequence: 0}`。因此新增派生形状把 projector 从 v6 升到 v7，但 Event 信封仍为 `tracegraph.session-event.v1`。

Web `AttachmentComposer` 默认 offload，并在本地先做类型、空文件、5 MiB 与 8 个上限提示；服务端仍独立重验。Trajectory 的附件卡片展示 durable added/rejected/offloaded 与 PDF 抽取状态；在线模式按需加载图片 Blob URL 或提供 PDF 下载，并在替换/卸载时撤销 URL。Replay 只展示当时投影的 metadata/status，附件预览明确禁用，避免 replay bearer 越过所选历史前缀读取二进制。
