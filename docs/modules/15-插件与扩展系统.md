# 模块 15：插件与扩展系统（G-17）

> 定位：为受信的 Host 内组件提供可逆生命周期和六个有界扩展点，同时保持 Ledger、权限与 recovery 边界在 Host/Core 手中；Sandbox/WAL 仍是具体 executor 的显式能力，不由注册动作自动获得。
> 代码：`packages/contracts/src/extension.ts`、`packages/core/src/extension.ts`、`packages/core/src/tool-registry.ts`、`packages/core/src/runtime.ts`、`apps/cli/src/extension-config.ts`、`packages/host/src/index.ts`、`packages/sdk/src/index.ts`、`apps/web/src/`
> 实现状态：**已实现/已验证**；`EXTENSION_API_VERSION = "tracegraph.extension.v1"`；G-17 完成时 canonical Event 共 77 种/projector v7，经 G-08/G-10/G-11/G-12/G-20 后当前为 102 种/projector v9

---

## 1. 它是什么，又不是什么

`ExtensionManager` 是一个受信的进程内能力组装层，不是任意第三方 JavaScript 的安全沙箱。它为每个扩展提供六个 seam：

| seam | 用途 | 不能绕过的边界 |
|---|---|---|
| `registerTool` | 注册 strict input/output、timeout、side-effect 已知的 Tool | 仍经过模型工具白名单、Permission/Policy、Receipt/Observation；OS Sandbox/WAL 必须由该 Tool 的受信 executor 显式接入 |
| `registerTelemetrySink` | 复用 G-15 有界 Telemetry 信号 | 失败不能改写 Ledger，也不会成为事实源 |
| `registerContextStrategy` | 向当前轮次增加小型、不可信的 Context contribution | 最长 2,000 字符，facts 最大 16 KiB，超时/非 JSON 拒绝 |
| `registerPolicyRule` | 注入 Host 信任边界中的 strict policy rule | 只是额外决策层，不能突破 preset ceiling、Workspace capability 或 Plan Mode |
| `registerCommand` | 提供有界运维/诊断命令 | 返回 strict `ExtensionCommandResult`；需要业务写入时必须转为 Tool 而非偷写状态 |
| `on(event)` | 只读订阅已提交的 canonical Event | 收到 deep-cloned/frozen 值；不允许修改 Event 或阻止 Run |

每次注册都返回 `Disposable`。卸载时按 LIFO 回卷；激活中任一注册失败，本次已完成的注册也全部撤销。工具、策略、命令和 Context strategy 的名称冲突均 fail-closed，不做静默覆盖。

## 2. 版本与配置安全

扩展必须声明精确的 `api_version` 。与 `EXTENSION_API_VERSION` 不一致时，`activate()` 根本不会被调用，状态记为 `rejected` 并返回 `extension_api_version_mismatch`。

标准 CLI 默认读取 `<dataDir>/extensions.json`，也可用 `--extension-config <absolute path>` 或 `TRACEGRAPH_EXTENSION_CONFIG` 指定文件。这个文件：

- 是 strict `tracegraph.extensions-config.v1` JSON，最大 256 KiB，拒绝 symlink、非普通文件、重复项与未知字段；
- `module` 只是 Host-owned catalog key，**不是**文件路径或 npm specifier；
- 当前 trusted catalog 只包含 `@tracegraph/builtin-artifact-tools` 和 `@tracegraph/builtin-run-state-tools`；
- Core/CLI 不会 `import()`、`require()`、解析或执行工作区中的 `tracegraph.config.ts`/TS/JS。

因此“数据文件选择 Host 预先安装的扩展”与“从不可信仓库执行插件代码”是两件不同的事。后者当前明确不支持。

## 3. 内置能力已走同一个扩展面

G-17 没有只添一个空接口。它落地时把原有八个 Tool 拆成两个可逆内置扩展；G-08 又把五个 Team Tool 加入同一个 run-state 扩展，因此当前这两个扩展共贡献十三个 Tool：

- `@tracegraph/builtin-artifact-tools`：`read_artifact`、`list_artifacts`；
- `@tracegraph/builtin-run-state-tools`：`todo_read`、`todo_write`、`spawn_subagent`、`send_subagent_message`、`list_subagents`、`interrupt_subagent`、`team_read`、`team_task_write`、`team_mailbox_send`、`team_mailbox_claim`、`team_heartbeat`。

`read_file`、`list_dir`、`search`、`preview_patch`、`commit_patch`、`run_test` 仍是最小执行内核。关闭 Artifact 扩展后，下一个 Run 的模型 schema 中不再出现这两个 Tool，而 Todo/子 Agent/Agent Team 组与核心工具仍可用。G-10 的 `load_skill` 由 run-state 组装，但 Skill registry 是独立的数据扫描器。`createDefaultToolRegistry()` 当前兼容完整的 20-Tool 组装。

G-11 MCP native stdio bridge 现在通过同一 `TraceGraphExtension`/`registerTool` 进入权限、账本和恢复边界；HTTP/SSE、PTC 和动态第三方加载仍明确不支持。

## 4. Run lease、热重载与恢复

每个 Run 启动时获得 `ExtensionRunLease`，冻结：

- API version；
- manager generation 与 config digest；
- active extension names；
- 精确 active tool names。

这个 snapshot 进入私有 recovery v5 Artifact。恢复时如果当前扩展面与冻结 digest/Tool 集合不一致，Runtime fail-closed，不会用新插件重跑旧 Run。

reload/deactivate 只能在没有 active Run lease 时执行；激活/卸载期间也不允许新 Run 观察到半更新状态。替换扩展激活失败时，manager 会先尝试恢复旧注册集；恢复也失败则报出明确的 rollback failure。这是“idle-only hot reload”，不是对活动 Run 做 HMR。

## 5. 错误隔离与 `extension.error`

Event hook 和 Context strategy 使用独立超时、deep clone 与 deep freeze。某个扩展抛错时，Runtime 继续主 Run，并用唯一幂等键追加 `extension.error`，其 payload 只包含扩展名、API version、phase、有界 code/message 和必需的 source Event id/type。

`extension.error` 自身绝不再分发给 hooks，因此失败 hook 不能制造递归错误风暴。若 hook 在 terminal Event 提交后失败，Ledger 允许追加这一条维护性错误事实；Run 的 terminal outcome 不会被改写，消费者也不应假设 timeline 的最后一条必然是 terminal Event。

Telemetry 扩展 sink 仍是 best-effort 旁路；Tool 执行失败仍由标准 Receipt / `tool.failed|unknown` 表达，不用 `extension.error` 取代业务结果。

扩展代码本身已在 Host 进程信任边界内，manager 不能阻止它绕开 API 直接做副作用。当前随 Host 发布的静态 catalog 只有 read/none 的 Artifact 与 Run-state Tool；G-11 MCP native bridge 可按远端 hint 映射 read/write，但没有新增 write/execute executor。MCP 或其它副作用 Tool 除了注册 schema，还必须显式复用相应 Sandbox/WAL/幂等与崩溃对账适配器；仅调用 `registerTool` 不会自动获得这些保证。

## 6. Host、SDK 与 Web

Host 只暴露三个 strict 控制面：

- `GET /api/extensions`：返回名称、API version、`active|inactive|failed|rejected`等状态、registration count、generation 和脱敏错误；
- `POST /api/extensions/reload`：带 `command_id`、目标扩展与可选 expected config digest，受 command-id 幂等表保护；
- `POST /api/extensions/commands/:name`：路径与 body name 必须一致，args 最多 64 个，同样幂等。

这些路由既有 loopback bearer/Origin 边界保护；SDK 对响应重新 strict parse，401 仍沿用一次令牌刷新重放。Web Settings 仅展示安全状态并触发 idle-only reload，不上传代码、不显示本机配置路径，Replay 中不开放可变操作。

## 7. 验证与明确边界

| 层 | 主要证据 |
|---|---|
| Contracts | API/config/status/command/error/recovery snapshot strict schema；G-17 当时 77-event、当前 102-event 集合 |
| Core | 六个注册点、LIFO disposer、激活回滚、API mismatch、hook 超时/隔离、lease/reload 竞态、内置组卸载与 recovery v5 |
| Host/SDK/CLI | trusted catalog/data-only config、symlink/大小/未知 id 拒绝、三条 route、幂等与 401 replay |
| Web | Settings 状态、generation、错误与 reload；Replay 只读 |
| Evals | hook failure 只产生一条 `extension.error`且 Run 完成；卸载一个内置组后其余 Run 正常；API mismatch 未执行 activate |

当前没有任意 npm/本地路径插件加载、不可信代码沙箱、扩展 UI 注入、活动 Run HMR、完整 DI 容器；G-11 已提供 Host-owned stdio/native MCP bridge，但仍没有 PTC、HTTP/SSE、resources/instructions 或远程 registry；G-12 LSP 是独立的 Host-owned stdio/native seam，不属于第三方扩展动态加载面。Skill 已由独立 G-10 本地 `SKILL.md` 子系统提供。这些边界不应由“有一个扩展管理器”推导成已完成能力。
