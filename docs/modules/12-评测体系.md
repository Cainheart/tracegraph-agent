# 模块 12：评测体系

> 定位：与单元/集成测试分离的离线可执行评测，锁定关键 Runtime 行为、性能门、质量对比、文档一致性与 Trace 时间旅行确定性。  
> 入口：`vitest.evals.config.ts`、`evals/`、`packages/test-support/src/mock-provider.ts`  
> 最后核对：2026-09-19  
> 实现状态：**已验证**

---

## 1. 命令与边界

```bash
# 常规测试：不收集 *.eval.ts
pnpm test

# 离线评测：验证已提交基线并产生报告
pnpm evals

# 只有显式 update mode 才可改写已提交基线
pnpm evals:update
# 等价：pnpm evals -- --update
```

`pnpm evals` 先 build workspace，再通过独立 Vitest 配置只匹配 `evals/**/*.eval.ts`。它不改变 `pnpm test` 的收集语义。`typecheck` 另外调用 `typecheck:evals`，因此评测源码也必须经过 strict TypeScript 检查。

默认验证模式只读 `evals/baselines/performance.json`；只有 `TRACEGRAPH_EVAL_UPDATE=1`、`pnpm evals:update` 或显式 `--update` 才进入基线更新模式。基线变更是审查边界，不是普通验证运行的自动副作用。

## 2. 离线执行与报告

`evals/support/offline-guard.ts` 在每个 worker 中：

- 删除常见 provider/API key/token/secret 环境变量；
- 拦截 `fetch`、TCP 与 TLS 外连；
- 只允许 `127.0.0.1` / `localhost` / `::1`，供真实 Host/SSE 环回评测使用；
- 保留本地 Unix-domain socket，不把本机 IPC 误判为外网。

`ScriptedMockProvider` 是有界、零网络的 `ModelAdapter`：脚本最多 64 步，单个响应最多 64 KiB，总脚本最多 512 KiB，模拟超时最长 30 秒。它能返回固定 Decision/摘要、明确的非法输出、usage 回调和可取消超时；脚本耗尽后 fail-closed，不重复上一个响应。

每次运行把有界报告写入 `_tmp_evals/reports/latest.json`：最多 512 条测试、64 条性能观测，总计不超过 256 KiB，不收集 assertion payload 或 stack trace。`_tmp_evals/` 是 gitignore 的临时诊断产物，不是 canonical Ledger，也不是应提交的基线。

## 3. 五类评测

### 3.1 Runtime 行为回归

`evals/runtime/` 有 9 条独立用户路径：

| 评测 | 锁定行为 |
|---|---|
| `approval-chain` | preview 先于 approval，单次审批后才能 Patch，事件顺序与文件结果一致 |
| `compaction-trigger` | 真实 Runtime 跨过 Context 预算后触发严格减量的压缩链 |
| `tool-parallel` | 安全非写工具达到预期并发峰值，durable Observation 仍按请求顺序 |
| `crash-recovery` | 模拟 Host 丢失后在同一 Ledger 恢复，旧 approval 失效、新 authority 成功 |
| `sandbox-refusal` | read-only hard constraint 在审批/WAL/改盘前拒绝 mutation |
| `subagent-delegation` | 两个 child 各自产生 started + initial message + terminal，父侧正好 6 条 `subagent.*`，child Session/Ledger 可独立读取并在新 Runtime 中重放 |
| `attachment-multimodal` | 5 MiB + 1 byte 形成 durable `too_large` rejection；不支持图片的模型收到零 image block；PDF 抽取失败显式降级为 `reference_only` |
| `extension-system` | hook 抛错被隔离为单条 `extension.error`；卸载 Artifact 扩展只改变后续 Run Tool surface；API version mismatch 在 activate 前拒绝 |
| `agent-team` | mailbox 在新 Runtime 重放后不丢；heartbeat timeout 以一个 loss fact 原子 reopen 且不自动重派；并发 claim 只有一个 owner |

这些用例运行真实 `AgentRuntime`、Ledger、Workspace 与相关域服务；只有 provider 是可编程替身。

### 3.2 质量对比

`evals/quality/` 以同一任务的 baseline/augmented 成对评分：

- `memory-context-quality.eval.ts` 保留旧 `retrieveMemoryFixture` 的回归证据，检查 command accuracy、最小 edit scope、source grounding、offline boundary 与跨项目拒绝；它只代表 fixture seam，不承担生产检索排名的证明。
- `retrieval-rag-quality.eval.ts` 使用真实 `createLocalRetrieval()`，对 3 份受控文档执行 ingest → BM25 search → `readChunk()`。它记录 `retrieval.task_success_rate.without/with` 与 `retrieval.citation_accuracy.without/with`；当前固定数据集的期望是两项都从 0 提升到 1，并校验 source path、命令所在行区间和 chunk 正文一致。
- CodeGraph 对比复制真实 failing TypeScript fixture，调用 `analyzeCodeGraph`产生 `static_module_unresolved` 诊断，检查故障定位、修复选择、最小编辑面和诊断可追溯性。

这些评分是确定性代理指标。新 G-21 用例证明生产本地 JSONL/BM25 链路、命中内容与 citation provenance 在受控任务上不会退化；它仍不是真实 LLM、开放域语料、embedding/vector backend 的通用质量排行或生产成功率。

### 3.3 性能门

`evals/perf/performance.eval.ts` 测量一条确定性代表路径，并对四个可审查 gate 与 `evals/baselines/performance.json` 比较：

1. `context.built.input_tokens`：必须发生压缩的长上下文输入 token；
2. `run.model_calls`：直接回答 Run 的模型调用数；
3. `tool.call.p95_ms`：20 次本地有界 `read_file` 的 P95；
4. `sse.first_byte_ms`：真实 loopback Host Ledger stream 的首字节时间。

token 与 model-call 基线是确定性上限；两个 wall-clock 基线保留较大的 scheduler/startup 余量，只是回归报警，不是对所有机器的 SLA 声明。评测还构造人为过低的 token 和 latency 上限，反向证明 gate 会 fail-closed。

### 3.4 文档一致性

`evals/docs/implementation-consistency.eval.ts` 从明确白名单核对：

- 公开标识符在实现与指定文档中同时存在；
- 独立 schema/storage 版本字面量与文档同步；
- 文档中的 durable Event 存在于 canonical `EventTypeSchema`；
- G-08 的 13 个 team Event、G-12 的 2 个 LSP Event、当前 102-event 总数、projector v9、recovery v5 与 20 个 built-in Tool 保持同步；
- 文档中的 Host method/route 确已注册；
- README 里的验证命令存在于根 `package.json` scripts。

这不是对所有自然语言声明的完全语义证明；白名单外的文档仍需人工评审。

### 3.5 Trace Replay 时间旅行

`evals/replay/time-travel.eval.ts` 覆盖 G-23 的 durable replay 不变量：

1. 先对一个完整 Run 的每个 sequence 保存 canonical `ReplaySnapshot`；
2. 用新的 `AgentRuntime` 从同一份磁盘 JSONL Ledger 逐序列调用 `replayAt()`；
3. 核对 projection、anchor event/hash 与 `snapshot_hash` 在重启后保持一致；
4. 检查 forward diff 能表达 Tool result、Artifact evidence 与 Approval 变化；backward/same 方向及 Todo/Plan/status/mode 字段由 Core 单测覆盖；
5. 比较回放前后的 Ledger，证明 replay 只读且没有追加 Event。

这里验证的是 canonical Ledger → `RunProjection` 的确定性，不是整个 Web `WorkbenchSnapshot`。浏览器的连接状态、项目列表、volatile model surface 与异步 Artifact 展示状态都不进入 canonical snapshot hash；UI 步进、停流、generation gate 与只读控件由 Web 单测覆盖，当前仍没有 Playwright 真实浏览器 E2E。

## 4. 版本与明确限制

G-16 只增加评测、fixture、根脚本与文档，**没有新增或修改生产 Session Event/Projection 契约**。因此：

- `SCHEMA_VERSION` 仍为 `tracegraph.session-event.v1`；
- G-16 当时的 `PROJECTOR_VERSION` 为 `tracegraph.projector.v5`；后续 G-07 增加 `subagents` 派生形状升到 v6，G-18 增加 `attachments` 后为 v7，G-08 增加可选 `team` 后为 v8，G-20 增加可选 `code_intel` 后当前为 `tracegraph.projector.v9`；
- 评测 report/baseline 的 schema 只属于开发工具，不进入 Runtime Ledger。

G-23 增加独立的 Replay Snapshot/Diff v1 envelope，但没有新增 Session Event，也没有改变既有 Projection 字段语义；所以同样不提升 `SCHEMA_VERSION` 或 `PROJECTOR_VERSION`。Replay eval 只读已有 Ledger，不生成第二套回放事实。

G-21 追加 `memory.written`、`memory.recalled`、`retrieval.index_updated` 三种 Session Event，使总数当时变为 68；既有 `memory.candidate_evaluated` 也已有 Runtime 生产者。因为 Event 信封和 Projection shape 未改，`SCHEMA_VERSION` 当时仍为 v1、`PROJECTOR_VERSION` 仍为 v5。后续 G-07 追加 5 种 `subagent.*` Event 并增加 `RunProjection.subagents`，G-18 再追加 3 种 `attachment.*` Event 与 `RunProjection.attachments`，G-17 再追加 `extension.error`，G-08 最后追加 13 种 `team.*` Event 与可选 `RunProjection.team`，G-10/G-11/G-12 再追加 Skill/MCP/LSP 事件，G-20 再追加两个 `code.*` Event 与可选 `RunProjection.code_intel`，所以当前总数为 102、`SCHEMA_VERSION` 仍为 v1、`PROJECTOR_VERSION` 为 v9。检索 request/response/index 使用独立 `tracegraph.retrieval.v1`，不能与 Session Event 版本混用。

G-07 的 runtime eval 证明有界父子委派、独立 child ledger 与父侧 6 条 lifecycle 回执；G-08 的 Agent Team eval 另验证 mailbox 重启持久性、heartbeat timeout 原子 reopen 且不自动重派，以及并发 claim 单 owner。两者都不把同步阻塞的单个 `spawn_subagent` 冒充成通用非阻塞父循环，也不证明真实 provider、多 Host 协调或浏览器 E2E。

G-18 的 runtime eval 证明附件约束会穿过真实 `AgentRuntime` 路径，而不只是契约解析器单测；它不证明真实外部模型的 vision 质量、PDF OCR、运行中 steering 附件或 Replay 二进制预览。

G-17 的 runtime eval 以三个场景覆盖真实 Runtime hook/error、内置扩展可逆卸载和 API mismatch；它不证明任意第三方代码安全，标准 Host 也不加载这类代码。

G-22 已把离线评测与性能/文档/时间旅行审计接入独立 CI job，并增加覆盖率、供应链和发布门。当前还没有 Playwright 真实浏览器 E2E、真实外部 provider/Collector、真实大语料 retrieval 质量评测、embedding/vector backend 对比或多机性能校准，也尚未取得可引用的 GitHub-hosted run URL；本地三个文档任务的 BM25 指标不能冒充这些外部证明。
