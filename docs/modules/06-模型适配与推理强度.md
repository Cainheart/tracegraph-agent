## 1. 接缝设计

模型侧的主接缝是 `ModelAdapter`（`types.ts`）：

```58:62:packages/core/src/types.ts
export interface ModelAdapter {
  readonly name: string;
  capabilities?(): ModelCapabilities;
  usageIdentity?(): { provider: string; model: string };
  publicRequestMetadata?(input: ModelInput): PublicModelRequestMetadata;
  decide(input: ModelInput): Promise<unknown>;
  summarizeContext?(input: ContextSummaryInput): Promise<unknown>;
}
```

两点值得注意：

- `decide()` 返回 `unknown` 而**不是** `Decision`。校验责任明确地在调用方（Runtime）——适配器只负责取回内容。
- `summarizeContext()` 是 G-02 专用的可选请求；它不返回 Decision，也不获得工具能力。Provider 返回仍是 `unknown`，由 Context 层用 strict `ContextSummarySchema` 校验并决定是否降级。
- `usageIdentity()` 为 preflight meter 提供稳定 provider/model；无效或抛错会被 Runtime 收敛成安全 fallback，不阻断 Run。
- `capabilities()` 是 G-18 的 Host-owned 能力声明；缺失、无效或抛错都 fail-safe 为 `{image_input:false}`，Runtime 不从 provider/model 名称猜测图片能力。
- `publicRequestMetadata` 是**可选**的，它只暴露可公开的请求元数据（供应商、模型名、推理强度、适配器名），供事件与 UI 使用。

`ModelInput` 还带 `toolSchemas: readonly ModelTool[]`：Runtime 每轮从 Registry 的显式模型投影注入，provider 不自行维护硬编码工具表。G-18 的可选 `images` 只可能来自已经 stage/claim、通过 hash/MIME/scope/能力校验且由用户显式选择 inline 的 PNG/JPEG，并且只附在首个模型请求。另有两个互相独立的 best-effort 回调：`onPublicProgress` 只服务易失公开画面；`onUsage(ModelUsageReport)` 把完整 provider 响应中的用量交回 Runtime，后者再写 durable Event。任何 usage 缺失、畸形或 callback 异常都不能让原本有效的模型响应失败。

`ModelRequestError` 携带 `code`，是"请求没成功"与"内容不合规"的分界线；Runtime 据此区分 `model.request_failed` 与 `model.output_invalid`。

## 2. 供应商与协议

```15:17:packages/core/src/model-provider.ts
export const MODEL_PROVIDERS = ["openai", "deepseek", "glm", "qwen", "minimax", "anthropic", "custom"] as const;
export type ModelProvider = typeof MODEL_PROVIDERS[number];
export type ModelProtocol = "openai-chat-completions" | "anthropic-messages";
```

**7 个供应商、2 种协议。** `glm` / `qwen` / `minimax` / `custom` 都走 OpenAI 兼容协议，区别只体现在推理强度支持与 JSON mode 判定上。

`ConfigurableModelAdapter`（`name = "configurable-model-provider"`）是唯一实现，运行时可被 `configure()` 重新配置：

| 校验 | 拒绝条件 |
|---|---|
| 协议 | 非 `http:` / `https:` |
| URL 凭据 | `url.username` 或 `url.password` 非空 |
| 必填 | `model` 去空格后为空；`credentialRef` 不是严格的 `${secret:NAME}` |
| 枚举 | provider / protocol 不在白名单 |

`ModelProviderConfig` 只保存 `credentialRef: SecretReference`，不保存 `apiKey`。`configure()` 还会去掉 `baseUrl` 末尾的斜杠（`replace(/\/+$/u, "")`）。未配置时 `decide()` 抛 `model_not_configured`；`publicConfig()` 返回默认值 `openai / openai-chat-completions / https://api.openai.com/v1 / gpt-4.1-mini` 且 `configured: false`，也不含引用或值。

### 2.1 请求前一刻解析凭据

`decide()` 每次请求都通过注入的 `resolveCredential(reference)` 把 `${secret:NAME}` 解析为短生命周期的 `ResolvedModelProviderConfig.apiKey`。解析失败统一变成 `model_credential_unavailable`，过短值变成 `model_credential_invalid`；适配器不会把底层 Keychain/文件错误详情带进事件。解析成功后立即用 `registerSecretForRedaction()` 登记精确值，再交给协议请求函数。

这条边界意味着：配置、事件与公开元数据只看到引用或安全元数据；明文只在本机 Host 发请求所需的内存与 HTTP header 中短暂存在。存储后端选择和迁移由 CLI 装配层负责，见模块 11。

## 3. Decision 的四条请求路径

`decide()` 先按协议分派，再按**是否存在 `onPublicProgress` 回调**决定走流式还是非流式：

| 协议 | 非流式 | 流式 |
|---|---|---|
| `openai-chat-completions` | `callOpenAICompatibleJson` | `callOpenAICompatibleStream` |
| `anthropic-messages` | `callAnthropicMessagesJson` | `callAnthropicMessagesStream` |

即：**只有需要实时展示的调用方（Host/Web）才付流式的代价**，测试与批处理走 JSON 路径。

无图片时请求体结构一致：

```
messages: [
  { role: "system", content: systemPrompt(mode, toolSchemas) },
  { role: "user",   content: JSON.stringify({ turn, context }) },
]
```

Runtime 已把任务、历史与 Observation 组装进 canonical `context`；provider wire 只发送 `turn + context`，避免重复 task/observation 使 token 账目失真。它仍是一条 JSON user message，而不是 provider-native 多轮消息；好处是确定性与可复现，代价是模型看不到原生消息边界结构。

G-18 inline 图片只扩展首次 user content：OpenAI-compatible 使用 `image_url` data URL block，Anthropic 使用 `{type:"image",source:{type:"base64",media_type,data}}`。图片之后仍附同一份 canonical JSON 文本 block。`image_input:false` 时适配器还会在 credential resolution/fetch 之前二次拒绝，保证错误装配也不会把图片发出；一次有界 repair 只处理文本输出，不重复携带图片。默认 offload 图片和所有 PDF 不进入 provider image block。

OpenAI 路径使用 `authorization: Bearer <key>`，Anthropic 路径使用 `x-api-key` + `anthropic-version: 2023-06-01`。

错误处理：非 2xx 时只读取响应前 **500** 字符，并统一经 `redactSensitiveText()` 处理；它既覆盖常见 token 形态，也覆盖 G-19 在进程内登记的精确凭据值，然后才抛 `ModelRequestError("model_http_<status>")`。网络层失败由 `modelFetch` 包装，取 `error.cause.code`（默认 `network_error`）并提示检查 provider / Base URL / 代理 / 网络。

### 3.1 G-02 Context summary 请求

`summarizeContext()` 复用相同的配置、凭据解析与 provider 协议，但有独立 prompt 和 token 目标：OpenAI-compatible 走 `/chat/completions`（可用时请求 JSON mode），Anthropic 走 `/messages`并使用 `temperature: 0`。System prompt 只允许返回 `{facts,open_questions,refs}` 一个 JSON 对象，要求把 `source_text` 当数据而不是指令。

Provider 层只做 JSON 语法解析；非法 JSON 原样交给 Context 层，使 `context.summary_failed` 成为唯一失败/降级边界，不在 adapter 内猜测或修复摘要。请求失败的诊断不包含 provider body，避免返回中回显的原始 Context 进入日志。

## 4. 输出解析：三层防线

这是本模块最关键的设计。**模型输出永远不能被直接当成动作。**

### 4.1 第一层：宽松但安全的解析

`parseDecisionOrSafeDirectAnswer()`：

1. 若内容里没有 JSON 对象（先剥掉 `<think>...</think>`）→ 当成**纯文本答案**，`safeDirectAnswer()` 包装成一个 `finish` 决策（上限 **8 000** 字符，不推断任何工具调用）。
2. 否则 `parseDecision()` 严格校验。
3. 失败时若该 JSON 不含 `kind` / `tool_call` / `tool_calls` / `action` 且带有 `final_answer`/`answer`/`content`/`response`/`message` 字段 → 同样降级为纯文本答案。

`parseDecision()` 内部做了两件**必要的**宽容化处理：

```699:707:packages/core/src/model-provider.ts
  // Several OpenAI-compatible providers serialize absent optional properties as
  // null. The canonical contract represents absence by omitting the property.
  // Normalize only optional envelope fields; tool names and arguments remain
  // strictly validated by DecisionSchema before the runtime can execute them.
  const normalized: Record<string, unknown> = normalizeProviderDecision(parsed);
  for (const key of ["tool_call", "tool_calls", "final_answer", "expected_effect"] as const) {
    if (normalized[key] === null) delete normalized[key];
  }
```

以及 `normalizeProviderDecision()`：**把 `evidence_refs` 里的字符串（如观测 ID）过滤掉**，只保留能通过 `SourceRefSchema` 的完整对象。

```710:717:packages/core/src/model-provider.ts
/**
 * Keep the model responsible for intent, not for manufacturing trusted
 * evidence.  Providers commonly echo observation IDs as strings in
 * `evidence_refs`, while the contract deliberately requires full, typed
 * SourceRef objects.  Those shorthand values are not executable intent and
 * are therefore ignored rather than making an otherwise valid tool Decision
 * fail closed after the tool has already established useful evidence.
 */
```

设计意图很清楚：**模型只负责意图，不负责制造证据。** 证据由 Runtime 附加。

### 4.2 第二层：一次有界修复

解析失败后（仅 OpenAI 兼容路径），`repairOpenAICompatibleDecision()` 发**一次**修复请求：`temperature: 0`，原始输出截断 **12 000** 字符，system 提示强制：

- 只返回 `kind: "finish"`；
- 明确禁止 `tool_call`、`tool_calls`、`action_id`、`patch`、`approval`、隐藏推理；
- 给出精确的目标 JSON 形状。

返回值若不是 `finish` 立即抛 `TypeError("Model response repair attempted a non-finish Decision")`。

**修复通道在物理上无法产生副作用**——这条约束不依赖模型守规矩，而由代码强制。

### 4.3 第三层：安全兜底

`safeFormatFallback()` 是本模块的最后一道闸门：

- 先尝试从宽松 JSON 中**只读恢复**文本答案；`directAnswerFromSafeLooseJson()` 会在发现任何动作痕迹时直接放弃：

```660:663:packages/core/src/model-provider.ts
  // Any indication of an action makes the object ineligible for recovery.
  // We do not guess intent from partially-valid agent envelopes.
  const actionKeys = ["tool_call", "tool_calls", "tool_name", "action", "action_id", "arguments", "patch", "approval"];
  if (actionKeys.some((key) => key in parsed)) return undefined;
```

- 都失败则返回一段中文提示，说明"模型已返回内容但格式无法安全转换，TraceGraph 已停止任何未验证的工具动作"。

**结论：格式漂移不会变成工具调用，也不会变成无提示的静默失败。**

## 5. 流式与公开画面

SSE 解析是自研的（`providerSseData`），**Core 不依赖浏览器 SDK**：按 `\n\n` 分帧，取 `data:` 行，`[DONE]` 终止（OpenAI）。Anthropic 侧只取 `type === "content_block_delta"` 且 `delta.type === "text_delta"` 的片段。

`createPublicReasonProgress()` 是最讲究的部分。它从持续累积的 Decision JSON 中只提取两个显式字段，但**必须等该字段的闭合引号到达后才发布**：

| 字段 | 上限 |
|---|---|
| `public_reason` | 360 字符 |
| `final_answer` | 8 000 字符 |

四条硬约束：

1. **完整字段后再发。** provider 即使把 opaque Key 逐字符拆进 SSE chunk，浏览器也收不到可重组的未脱敏片段；字段闭合后先对完整值做精确值与形态脱敏。
2. **只增不减。** 若解析结果不能以已发布内容为前缀，就等更完整的快照：

```417:420:packages/core/src/model-provider.ts
    // A parser prefix must only grow. If a malformed/escaped fragment would
    // rewrite earlier characters, wait for a later complete snapshot instead
    // of leaking a speculative or inconsistent display value.
    if (!value.startsWith(previous) || value.length <= previous.length) return;
```

3. **只发真实模型字符**，不做前端叙述、不转发原始 JSON、工具调用或参数。
4. **瞬时通道也做脱敏。** `safePublicProgress()` 复用 `redactSensitiveText()`（包括 G-19 登记的 raw/JSON-encoded 精确值），再去掉 `\u0000` 并截断。

`completeJsonStringField()` 手写了 JSON 字符串字段解码（含 `\"`、`\\`、`\/`、`\b`、`\f`、`\n`、`\r`、`\t` 与 `\uXXXX`），并在字段尚未闭合时返回 `undefined`。代价是公开更新粒度从 token/chunk 变成字段级，换来跨 chunk 凭据不变量。

**注意**：provider 的 `reasoning_content` / thinking 块**从不进入公开画面**。`PublicModelProgressUpdate` 保留了 `thinking_delta` 这个兼容 kind，但 Runtime 会丢弃它。

### 5.1 JSON/SSE usage 规范化

四条请求路径都在拿到完整 provider usage 后才触发 `onUsage`：

| 路径 | 解析口径 |
|---|---|
| OpenAI-compatible JSON | 接受 `prompt_tokens/completion_tokens` 或 `input_tokens/output_tokens`；解析 cached input 与 reasoning output details |
| OpenAI-compatible SSE | 仅 canonical `api.openai.com` 主动请求 `stream_options.include_usage: true`；其它 compatible origin 不强塞可选字段，但仍解析其主动返回的 usage；只在收到 `[DONE]` 后回调最后一个合法 usage |
| Anthropic JSON | 从顶层 `usage` 取 input/output，并把 cache creation/read input 纳入 input total；cache read 可单列 |
| Anthropic SSE | 合并 `message_start.message.usage` 与 `message_delta.usage`；只有 terminal usage 与 `message_stop` 都出现后才回调，截断流不把 start 阶段的 `output_tokens: 0` 误记成完整用量 |

所有 token 都必须是非负 safe integer，`total_tokens` 由规范化后的 input + output 生成。OpenAI-compatible usage 若明确同时提供非负 `cost` 和合法三字母 `currency`，才进入 `provider_reported_cost`；缺任一字段、格式非法或 provider 不回报成本时都省略，Runtime/Web 明示 `unavailable`，不查价目表推算。

OpenAI 初始请求使用 `request_kind: "initial", request_sequence: 1`；若 Decision 格式修复被触发，第二个 JSON 请求单独回报 `request_kind: "repair", request_sequence: 2`。Context summary 使用自己的 `model_call_id`、`request_kind: "summary", request_sequence: 1`。Runtime 会把 repair/summary durable 记录下来，但两者的请求形状都不等同于 Decision Context Manifest，因此不更新 initial request 的校准。Anthropic 当前没有 repair 请求分支，但已有 summary 路径。

## 6. 推理强度映射

`resolveReasoningPlan(config, requested)` 返回 `{ applied?, configuration, maxTokens?, requestFields }`，`configuration` 取值 `provider_default | native | mapped | unsupported`，并原样进入 `model.request_started` 事件。

| 条件 | applied | requestFields |
|---|---|---|
| `requested === "default"` | — | `{}`（交给供应商默认） |
| Anthropic + 自适应模型 | 见下 | `thinking: { type: "adaptive" }`、`output_config: { effort }` |
| `provider === "deepseek"` 且模型匹配 `^deepseek-v4-(flash\|pro)` | low→low、max→max、其余→high | `reasoning_effort`、`thinking: { type: "enabled" }` |
| `provider === "openai"` 且模型可映射 | 见下 | `reasoning_effort` |
| 其他（glm/qwen/minimax/custom、未识别模型） | — | `{}` |

OpenAI 模型映射（`mapOpenAIReasoningEffort`）：

| 模型前缀 | 映射 |
|---|---|
| `gpt-5.6*` | 原样透传 |
| `gpt-5.1-codex-max*` | `max` → `xhigh` |
| `gpt-5-pro*` | 恒为 `high` |
| `gpt-5*`、`o1/o3/o4*` | `xhigh`/`max` → `high` |
| 其他 | 不支持 |

Anthropic 自适应模型（`supportsAdaptiveAnthropicReasoning`）：`claude-(opus|sonnet)-4-(6|7|8|9)` 或 `claude-(opus|sonnet|fable|mythos)-5`；`claude-4-6` 上的 `xhigh`/`max` 被降为 `high`。`maxTokens` 在 `xhigh`/`max` 时为 **65 536**，否则 **16 384**；非流式 JSON 路径默认 `max_tokens` 为 **4 096**。

不支持推理控制时，Anthropic 路径会补 `temperature: 0`。

**关键取舍**：`requestFields` 只在能证明支持时才写。注释写得很直白——

```564:568:packages/core/src/model-provider.ts
  if (config.provider !== "openai") {
    // OpenAI-compatible endpoints do not imply support for OpenAI's reasoning
    // controls. Unknown/custom providers therefore receive no speculative key.
    return { configuration: "unsupported", requestFields: {} };
  }
```

宁可不发，也不猜测。

## 7. 系统提示词

`systemPrompt(mode, toolSchemas)` 承担四个职责：

1. **格式契约**：分别给出 `finish`、旧单 `tool_call` 与批 `tool_calls` 的精确 JSON 形状；单/批字段互斥，batch 为 1..16 且 action id 唯一，要求“恰好一个 JSON 对象，无周边散文或 Markdown 围栏”。
2. **动态工具说明**：工具目录完全来自本轮 `ModelInput.toolSchemas`，最终边界再次逐项重建为 `name/description/input_schema`。它会自然包含 Registry 提供的 `list_artifacts`，但绝不包含 `output_schema/timeout_ms/concurrency_safe/side_effect/max_result_bytes/execute/render`。因此新增/移除 Registry 工具不会与一份硬编码 prompt 目录漂移。
3. **批处理纪律**：只把彼此独立的调用放进同批；有数据依赖的动作分轮请求；实际并发、超时、权限、side-effect 顺序、输出校验与 render 都由 Host 决定，模型不能覆盖。
4. **证据与展示纪律**：一般性解释不得读仓；仓库问题必须有观测支撑；**“搜索零命中不等于不存在”**；`public_reason` 是简洁真实的公开摘要且不得包含隐藏思维链；`evidence_refs` 通常返回 `[]`；不得虚构工具调用。

另外包含一组输出呈现规则：`final_answer` 用可读 Markdown；对架构/流程/调用链/状态机类问题**优先**用 mermaid，并要求按关系类型选图（`flowchart` / `sequenceDiagram` / `stateDiagram-v2`）、节点用语义 ID 与可读标签（`web[Web client]` 而非 `A`）、分组克制、避免不支持的图标与装饰。这直接决定了 Web 端回答的观感。

OpenAI/Anthropic 的 JSON 与 SSE 四条 Decision 请求路径都调用同一个动态 `systemPrompt()`；summary 请求继续使用独立、无工具能力的 prompt。`mode` 只影响最后一句：plan 模式不得调用写或测试工具。

`model-provider.test.ts` 的 `requests structured Markdown, clear Mermaid diagrams, and only public reasoning summaries` 还断言动态目录包含注入工具/batch/`list_artifacts` 且排除全部 Host-only key；`parses a nullable-compatible batch Decision without collapsing it to one call` 覆盖 `tool_calls` 与 nullable normalization；`never recovers answer text from malformed JSON that also carries tool_calls` 证明坏 batch 不会被降级成看似安全的直接答案。四条 provider 请求路径都由这些共享构造函数覆盖。

## 8. 确定性假模型

`DeterministicFakeModel` 是默认适配器（未注入 `model` 时使用），也是一个**可执行的流程规范**——它按观测推进：

| 上一步观测 | 下一步决策 |
|---|---|
| （无观测） | `search { pattern: "return left - right;" }` |
| `search` | `read_file { path: first_match_path ?? "src/add.ts" }` |
| `read_file` 且摘录不含缺陷 | `finish`（"未发现预期缺陷，故未提出补丁"） |
| `read_file` 且 `mode === "plan"` | `finish`（"缺陷在 src/add.ts；plan 模式未修改工作区"） |
| `read_file` 含缺陷 | `preview_patch`（`left - right` → `left + right`，risk `high`） |
| `commit_patch` | `run_test { suite: "fixture" }` |
| `run_test` 且成功 | `finish`（"补丁已应用且测试通过"） |
| 其他 | `finish`（`Stopped after ${last.summary}`） |

它同时是三条能力的活证明：**plan 模式隔离**、**审批必经**、**测试收尾**。所有决策都经 `DecisionSchema.parse`，因此假模型与真模型走完全相同的校验路径。

## 9. 已知缺口

1. **两条协议的错误恢复能力不对称。** OpenAI 兼容路径有完整三层（严格解析 → 一次修复 → 安全兜底）；Anthropic 路径只有一层：

```321:321:packages/core/src/model-provider.ts
  return parseDecisionOrSafeDirectAnswer(content);
```

`callAnthropicMessagesJson` / `callAnthropicMessagesStream` 都**没有** try/catch，既不触发修复，也不触发 `safeFormatFallback`。解析抛错时直接以非 `ModelRequestError` 冒泡到 Runtime，被归类为 `model.output_invalid` 并终止 Run。Anthropic 用户在格式漂移时得到的是失败，而 OpenAI 兼容用户得到的是兜底答案。

2. **流式中断被当作格式问题，而非请求失败。** `providerSseData` 在流提前结束时只是正常退出循环，`content` 变成截断的 JSON，于是走"解析失败 → 修复 → 兜底"分支。**没有机制识别"传输中途断开"**，也没有把这类情况标记为不可信。

3. **无重试与退避。** 网络抖动与 5xx 直接变成 `ModelRequestError` 并使 Run 失败。唯一的"重试"是那次格式修复——且它只在格式错误时触发。

4. **`supportsJsonMode` 只认 openai 与 deepseek。** glm / qwen / minimax 实际支持 `response_format` 却拿不到，只能依赖三层解析与修复扛住格式漂移；注释解释了原因（兼容不代表支持），但代价是把确定性押在提示词上。

5. **模型名靠正则硬编码。** 新增模型（含同一供应商的新版本）必须改代码，`resolveReasoningPlan` / `mapOpenAIReasoningEffort` / `supportsAdaptiveAnthropicReasoning` 三处正则都要维护。没有配置化的模型能力表。

6. **API Key 在发请求时仍须以明文存在于 Host 内存和请求头。** G-19 已把持久配置改为引用、补上 backend 元数据与精确值脱敏，但当前没有锁页、硬件绑定或主动内存清零；非 macOS 私有文件后端仍是 `0600` plaintext-at-rest。这个限制不能被“配置文件不含明文”掩盖。

7. **`custom` 供应商能力最弱**：无 JSON mode、无推理控制，完全依赖解析回退链。

8. **`thinking_delta` 声明但被丢弃**，是契约/类型比实现宽的一处（见模块 01 与模块 02 的同类问题）。

9. **没有 provider API 级的 usage 补查。** JSON/SSE usage 已解析并交给 Runtime，但 provider 响应与 Event append 之间没有 WAL；进程若在该窗口崩溃，不能凭 request id 向 provider 自动补账。当前 G-04 是 Patch Action 专用，不覆盖 provider 侧补账。

10. **没有 bundled full-wire tokenizer / `count_tokens` adapter。** `usageIdentity` 让 Context meter 能按 provider/model 校准，但适配器不会在请求前调用 Anthropic `count_tokens`，也没有本地 OpenAI tokenizer。可选 section counter 只看到片段，当前 preflight 仍是 estimated/calibrated；provider-reported total 才是请求后口径。

11. **`systemPrompt` 仍是一段巨型模板字符串**，含大量中文自由文本规则，无法按任务类型裁剪（聊天与代码任务共享同一提示词，靠“是否涉及本仓库”的自觉区分）。G-05 已对动态工具目录、批形状和 Host-only 字段排除做精确断言，但其余自然语言纪律仍不可能逐句证明。
